## 1. 问题

上一轮正式矩阵（20 block × A0/A1/A2/C/D）是在**没有任何 class 声明**的形态下测的：
`class_map` 只被 BACKGROUND 目标写入，服务进程从未被分类，`SP_DSQ_LAT` 没流量。
所以那批数字只能算"NORMAL→COMP 路径 + BG"的收益。本轮要回答一个具体问题：

> 在**同一 expert、同一参数、同一数据集、同一窗口、同一 cgroup 放置**下，
> 只是把服务 cgroup 声明为 `class=LAT`（并把 BG 目标显式声明为 `BG`），值多少？

设计成块内配对 `Cc−C` 与 `Dc−D`，因此结论不依赖跨日/跨运行比较。

## 4. 结论：这条负载上，声明 LAT 值 0；自适应臂里还略亏

1. **固定 expert 下 class 声明是彻底的零结果**：Cc vs C = −0.01% / +0.05%，CI 跨 0，胜负 10/10。
   `SP_DSQ_LAT` 有了真实流量（上一轮 soak 已证明路径被喂），但对 goodput@SLO 没有贡献。
2. **自适应臂下略负**：Dc vs D = −0.18%（GET，CI 不含 0），p99 从 4.87ms 升到 5.35ms、
   p99.9 从 8.8ms 升到 12.1ms。方向在 1ms/2ms/5ms 三档一致。
3. **收益仍然全部来自 expert 的切片/预算参数**：Cc/Dc 相对 A0 的 +1.5% 与 C/D 相对 A0 的
   +1.6%/+1.6% 没有差别；而 C 相对 A0 的 +1.61% 与上一轮旗舰的 +1.62% 几乎重合——这是
   跨运行的一致性观察（目标 cgroup 不同，**不作为配对证据**）。
4. 机制上目前只能给**假设**：LAT 档是 1ms 片段 + 抢占优先，服务线程在这种排队主导的
   负载里被切得更频繁，尾部的调度事件反而增多；这能解释 GET 的 p99/p99.9 变差，但没有
   单独的调度事件计数证据支持，因此不写成结论。

**产品含义**：class 声明现在是可声明、可审计、可撤销的（上一轮），但**它不是性能开关**。
要主张"四分类路由的收益"，必须找到 LAT/CACHE 真正有区分度的负载（例如唤醒延迟主导、
或内存带宽竞争主导的场景），而不是这条 redis 服务负载。CACHE 档在这条负载里没有对应
工作集，因此本轮不涉及。

## 5. 不能声称的

- 单机、单负载（redis GET/SET + 一个 BG 生产者）、单 SLO 设定、n=20。
- 本轮只给服务声明了 LAT；**没有声明 CACHE**（这条负载没有内存密集层的真实工作集；
  CACHE 只在 `experiments/class_route_soak_sp3.sp3` 的存活压测里被喂过，那里不测性能）。
- `llc_affinity=True` 的 CACHE 分档、`SP_DSQ_SHARED` 仍未测。
- **块内改档未测**：本轮每块档位静态。写测试时发现"刷新增档为 NORMAL 会变空操作"的
  产品 bug 已修（`class-del` 而非 no-op）并加了 unit，但**修复不在本轮构建里**，
  因此本轮数据不覆盖该路径。
- 这不是"class 路由无用"的一般性结论；只说明**这条负载 + 这套参数**下它没有收益。
