EulerPilot v2 — 自动切换的停顿与唤醒延迟毛刺量化
记录时间 2026-10-22，schedpilot-sp3（<SP3-IP>），内核 6.6.0-schedpilot-sp3，8 vCPU。
方法 `experiments/auto_apply_downtime_sp3.sh` + `experiments/sched_switch_probe.c` +
`experiments/analyze_switch_downtime.py`；数据 `evidence/p2/switch-downtime-20261022/`
（`summary.json`、`watch.tsv`、原始探针二进制的 SHA256 记在 `raw-SHA256SUMS`）。
这是切换代价测量，不是性能实验，不构成任何"性能提升"结论。

## 1. 测法

- 状态观察：1ms 轮询 `/sys/kernel/sched_ext/{state,root/ops,enable_seq}`，仅在变化或每 100ms
  心跳时落一行，**每行立即 fflush**（这个文件是整场实验唯一的时钟基准）。
- 延迟观察：4 个进程各以 1ms 周期 `clock_nanosleep(TIMER_ABSTIME)` 绝对唤醒，
  记录 `(应醒时刻, 实际迟到)`；绝对 deadline 消除 sleep 累积漂移。
- 全部时间戳取 `CLOCK_MONOTONIC`，与内核同一时钟域，因此分段只做数值比较，无跨机对齐。
- 一次 `enabled → 非 eulerpilot → enabled` 的间隔定义为一次切换的**空窗（downtime）**：
  这段时间里没有 v2 策略在保护任何任务。
- 负载：16 个 CPU 忙等线程（2× vCPU），在租约交给自动通道后拉起，用它把 CPU PSI 推过
  路由的 20.0 阈值，从而由自动通道自己产生切换。

`enable_seq` 在实验期间移动 3 次（593→594→595→596），与观察到的 3 次 attach 一一对应，
说明没有未被注意的额外 enable 事件。

## 2. 结果：空窗时长

| 切换 | 方向 | 空窗 |
|---|---|---:|
| 1 | safe-basic → latency-balanced（升载后自动切换） | **665.0 ms** |
| 1（run1） | safe-basic → latency-balanced（升载后自动切换） | **665.0 ms** |
| 2（run1） | latency-balanced → safe-basic（撤载后自动回落） | **303.1 ms** |
| 1（run2） | safe-basic → latency-balanced（独立复跑） | **621.0 ms** |

第二轮（`evidence/p2/switch-downtime-20261022-run2/`）是修复脚本死锁后的完整端到端复跑，
`script_rc=0`、`cleanup rc=0`、收尾 `disabled`/0 pin。它只有 1 个空窗，因为回落发生在
探针停止之后；升载空窗 621.0ms 与 run1 的 665.0ms 相差 6.6%，说明时长稳定可复现。

两次都含 rollback 与 apply 两趟 detach/attach。665 与 303 的差异**本轮未分解**：
第一次还包含 `ep-schedctl` 的 cfg 快照与写入、首次 `wait_pins_settled` 稳定采样等路径，
需要分别计时才能归因。

## 3. 结果：唤醒迟到（4 探针的分布范围，非均值）

| 段 | 样本/探针 | p50 | p99 | p999 | max | ≥1ms | ≥5ms | ≥20ms |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| baseline 无 v2（fair） | 6369–6370 | 63–82 µs | 126–137 µs | 0.97–3.24 ms | 3.5–8.1 ms | 6–12 | 0–4 | 0 |
| **空窗 1（高负载）** | 665 | 1.06–1.61 ms | **13.2–16.1 ms** | 19.2–22.1 ms | **20.2–23.1 ms** | 436–528 | 16–25 | 1–4 |
| 切换后同负载（已 attach） | 5000 | 67–516 µs | 1.21–2.05 ms | 2.19–2.59 ms | 2.2–3.0 ms | 170–806 | 0 | 0 |
| **空窗 2（撤载后）** | 303–304 | 64–86 µs | 118–259 µs | 279–477 µs | 279–477 µs | 0 | 0 | 0 |
| 回落之后（已 attach） | 5000 | 67–88 µs | 123–158 µs | 268–1658 µs | 1.5–3.1 ms | 1–7 | 0 | 0 |

关键对照是**同负载的"空窗 1" vs "切换后"**：负载条件相同，只是策略在位与否，
p99 从 1.2–2.0 ms 恶化到 **13.2–16.1 ms（约 8–13 倍）**，max 从 2.2–3.0 ms 到
**20.2–23.1 ms（约 7–10 倍）**，且每探针出现 1–4 次 ≥20 ms 的迟到。

而**空窗 2 在撤载后几乎测不出毛刺**（p50 64–86 µs，与 baseline 重叠，max 477 µs）。
所以：空窗时长是确定的，毛刺幅度需要"空窗 × 负载过订"叠加，不能把 20 ms 全部归因于 detach 本身。

## 4. 结论：自动 apply 不能默认开，且需要比 3s 冷却强得多的抑制

同一次 120s 实验里自动通道切换了 **2 次**（升载切过去、撤载切回来），间隔约 46s，
`--auto-min-interval-ms 3000` 完全没挡住：负载是阶跃的，PSI 爬升/回落都能在几秒内穿过阈值。
按实测空窗 0.3–0.7 s 计，若策略随负载抖动反复切换，累积无保护时间与反复 detach/attach 的
扰动会显著超过收益。因此进默认路径之前至少需要：

1. 更长的最小驻留（dwell）：建议以"一个空窗的数十倍"为量级起点，而不是 3s；
2. 回落侧的迟滞（撤载后不要立刻切回），或只在计划窗口内切换；
3. 把切换代价写进决策依据：目标收益小于一次空窗就不切。

本次实验没有实现这些，它们现在有量化依据了。

## 5. 本轮自身缺陷（已修，如实记录）

1. `sched_switch_probe.c` 的 `watch` 分支 argc 判断写成 4（实际 3 个参数），**watch 从未启动**，
   第一次运行没有 `watch.tsv`；已修正并加时长上限与逐行 fflush。
2. 实验主体在杀掉负载后用了**无参数 `wait`**，它会等所有后台任务、包括长期运行的执行服务，
   因此脚本永久阻塞（两次超时都源于此，第一次还叠加了无时长上限的 watch）。
   已改为按 PID 等待，并让所有后台进程释放继承的 stdout（否则交互会话看不到 EOF）。
   因主体未跑到分析段，分析逻辑被抽成 `experiments/analyze_switch_downtime.py`，
   分析逻辑同时被抽成 `experiments/analyze_switch_downtime.py`，
   使分段可以在不重跑实验的情况下复算。
3. 修完的脚本已完整端到端复跑一次（run2，`script_rc=0`），并独立复现了空窗量级；
   `gcc -Wall -Wextra` 编译探针无警告，`py_compile`/`bash -n` 均通过。

## 6. 边界

- 负载是 CPU 忙等，不是服务请求-响应；1ms 周期唤醒探针只反映调度延迟维度，
  不代表真实服务尾延迟。赛题要求的加载场景 SLO 仍未实现。
- 空窗样本共 3 个（升载 2：665.0/621.0ms；回落 1：303.1ms），仍属小样本，
  未做多种子重复；未测切换期间的吞吐、丢包或已完成工作损失。
- 665/303 ms 内部构成未分解（见第 2 节）。
- 原始探针二进制（4×1.92 MB）留在 SP3 `/root/epv2-evidence/auto-downtime/`，
  仓库保存其 SHA256 与派生的 `summary.json`/`watch.tsv`，避免仓库塞入大文件。
- 自动 apply 仍不在默认路径；P1 未收口；v2 仍无任何性能结论。
