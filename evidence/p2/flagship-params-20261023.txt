记录时间 2026-10-23，schedpilot-sp3（<SP3-IP>），8 vCPU，内核 6.6.0-schedpilot-sp3，
redis 7.2.15。工具 `experiments/flagship_param_pilot_sp3.sh` + `analyze_openloop_raw.py` +
`analyze_matrix_blocks.py`；数据 `evidence/p2/flagship-pilot-20261023/`（pilot 块，含
`per_run.csv`/`comparisons.csv`；逐请求 `raw-*.bin` 留在 `SP3:/root/epv2-evidence/`，
块内 `SHA256SUMS` 已入库）。构建：修复 runnable task stall 之后
（`ep-sched-loader 45bdc3c0d64c…`，见 `evidence/p1/stall-runnable-20261023.txt`）。
**本文冻结参数，不产出性能结论**；pilot 块按协议 §6.1 不进正式表。

## 1. 冻结结果

| 参数 | 冻结值 | 依据 |
|---|---|---|
| offered 率 | **60000 rps**（GET、SET 各一段） | 40k 时 5ms 阈值已经贴顶（A0 good% 99.88–99.94），臂间差只剩 +0.02…0.12%；60k 时 A0 落在 96.86–98.12%，臂间差 +1.3…1.75% 且违例数量级为 6.6–11.5 万条 |
| SLO 阈值 | **5ms**（同时报 1/2/5/10ms 四档） | 5ms 是发生器标定阶段就在用的默认值，不是为臂间差挑出来的；同时报多档，使结论不依赖单一阈值 |
| BG 工作单位 | **`probe5s`**（`service_load_probe bg` 的 5s 窗，与在线门控同一个生产者） | 实测 26/26 窗全齐、164.1–165.3 单位/秒，跨臂跨率一致 |
| BG 最小工作率 | **140 单位/秒** | 实测带宽 164.1–165.3；140 ≈ 带宽下沿再留 ≈15% 余量，块间噪声（<1%）不会误触，真实饿死会触 |
| BG 最长等待 | **50ms** | 实测 A0 5.2–5.8ms、C 2.6–3.0ms、D 1.4–3.9ms；schema 下限就是 50ms，所以这是"最紧的合法值"，仍比最坏实测高 8.6× |
| 前向 p99 绝对上限 | **10ms** | A0 实测 7.26–9.62ms（会偶发越线），C 4.88–5.60ms、D 4.54–6.67ms（不越线）⇒ 在线门控有真实工作但不会被自身测量钉死 |
| 样本量 | **20 block**，臂内配对，`seed=20261024`，预热 10s、测量 60s | 协议 §6.2 旗舰初值 |
| 主指标统计 | 块内配对 goodput@SLO 增益百分比的中位数 + 配对 block bootstrap 95% CI（10000 次重采样，固定种子），另报 log-ratio 敏感性、胜负轮数、逐块散点 | 协议 §7 |

臂集合按协议主线取 **A0/A1/A2/C/D**（A1 = 同等观测但不挂载的 shadow，A2 = 静态 CPUWeight），
B 按开销问题保留。

## 2. 为什么是 60k：一次 offered 率扫描 + 一次阈值重建

阶段 1 只跑 A0（裸 redis，无调度器），每个候选率 1 块；good% 由逐请求原始件重建
（协议禁止由分位数推算 goodput），一次运行同时给出所有候选阈值：

| offered | A0 GET p50/p99/p99.9 (ms) | good% @1/2/5/10ms (GET) | good% @1/2/5/10ms (SET) |
|---|---|---|---|
| 20000 | 0.080 / 1.557 / 2.043 | 95.52 / 99.87 / 100.0 / 100.0 | 95.25 / 99.79 / 99.99 / 100.0 |
| 40000 | 0.093 / 1.698 / 5.070 | 97.92 / 99.23 / 99.89 / 99.95 | 97.44 / 98.83 / 99.89 / 100.0 |
| 60000 | 0.248 / 9.625 / 15.569 | 89.49 / 94.73 / 98.15 / 99.6 | 88.68 / 93.45 / 96.97 / 99.4 |

20k 与 40k 在 5ms 上都在天花板（0.1% 级的违例），任何调度改进都只能落在噪声里；
60k 已进入服务端排队（`peak_inflight` 1251–1606、deficit 约 1800 rps），
但客户端仍未饱和（achieved/offered = 100%、0 超时 0 停顿、发生器 CPU 0.63 核，
标定见 `evidence/p2/matrix-harness-20261023.txt`）。**旗舰点选在"服务开始排队、客户端还没落后"这个区间**，
而不是等臂间差异消失的那个点。

阶段 2 在候选率上跑 A0/C/D 各 2 块（60k）与 1 块（40k），配对结果：

| 冻结点 | 块内配对 goodput@5ms 增益（中位数，n=2） | p99 变化 | BG 相对进度 |
|---|---|---|---|
| 60k C | GET +1.43% [0.57, 2.30]、SET +1.69% [1.68, 1.70] | −36.1% / −36.4% | ×0.999 |
| 60k D | GET +1.30% [1.05, 1.55]、SET +1.75% [1.43, 2.08] | −34.1% / −37.6% | ×1.001 |
| 40k C | GET +0.12%、SET +0.04%（n=1） | −39.2% / −25.8% | ×1.003 |
| 40k D | GET +0.12%、SET +0.02%（n=1） | −34.1% / −26.1% | ×0.994 |

**这些数字是量具检查，不是结果**：n=1/2、无置信区间含义、pilot 不进正式表。
它们的作用只有两条——(1) 证明 60k/5ms 能分辨（40k/5ms 不能）；(2) 证明配对分析管道
（原始件重建 → 块内配对 → bootstrap）能跑通并产出 `per_run.csv`/`comparisons.csv`。

## 3. 一条必须写在前面的更正

上一轮同样配置的 pilot（修复前）里，60k/40k 的 **C/D 数字全部作废**：调度器在块中途被内核
以 `runnable task stall` 摘除（6/6 块），后半段测的其实是 fair 接管后的系统，而 harness 当时
只在块结束时记 `schedext.state`，块"看起来完成了"。修复后的这轮 pilot 里
C/D 块结束仍是 `enabled`、`degenerate=False`，且 `auto_switches` 与 `observations_rejected`
已经进入 `per_run.csv`（D 每块切换 1 次，属预期）。作废数据留在
`evidence/p2/flagship-pilot-20261023/pre-fix-contaminated/` 以备核对，本文不引用其臂间数字。

## 4. 冻结的不确定性（不粉饰）

- **单种子、单机、单负载**。60k 是"这台 8 vCPU VM 上 redis 单线程的膝点"，换机器就要重扫；
  协议要求的跨机/未见负载验证没有做。
- **阈值敏感性未消除**。5ms 是业务上说得通、且在标定阶段就存在的值，但 1ms 档下 A0 只有
  88.97–91.22%，臂间差方向相同、幅度不同——正式表要按四档同时给，读者可自查。
- **BG 门槛是"实测带宽 + 余量"推出来的，不是业务预算**：本项目的业务侧没有真实的
  BG 完成时间承诺，`max_bg_wait_ms=50` 受 schema 下限约束。这条要在最终汇报里明说。
- **p99 越线的语义**：10ms 绝对上限在 A0 上会偶发越线，说明"D 少切几次也许只是因为它
  的门更常被自己的测量卡住"——正式矩阵要同时报 `last_hold` 与 `switches_recorded` 才能分开
  这两种解释。
