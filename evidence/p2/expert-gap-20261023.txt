## 1. 先修一个测量件的 bug（否则后面的 elapsed 是假的）

`redis_openloop_probe.c` 的摘要把 `offered_at_ms` 与 `finished_at_ms` 都打印成
**同一行上的两次 `wall_ms()`**，即两者恒等。后果：任何用 `finished-offered` 算时长的消费者都会
除零；`analyze_matrix_blocks.py` 恰好有"elapsed 非法就退回声明窗口"的兜底，所以此前所有
goodput 数字**没有错**（探针自己的 goodput 用内部单调时钟，且与逐请求重算在各自阈值上一致到
0.019%），但**该字段本身是假的**。已修：测量开始处记一次 wall clock，摘要打印真实起止；
重编译后 `r1-safe-basic/inject.json` 的 `finished−offered = 45002ms`（声明 45s）✓。
探针哈希由 `86b62652aed2…` 变为 `5f0213fd2dff…`。

## 2. 设计：把"门控延迟的代价"拆成两个可独立测量的因子

上一轮门控实验测到了确定性的延迟（`D` 比 `Dng` 晚约 40s 才切换），但用注入期 goodput 去衡量
代价时被机器双稳吞掉。本轮改为：

```
代价 ≈ (在注入条件下，两个 expert 的单位时间差) × (延迟 40s)
```

第二个因子已有（门控实验，2s 分辨率轮询）；第一个因子用**固定 expert、不切换**的静态对照来量：
两个臂都在测量开始前就已应用并静置 10s，测量窗内没有任何切换、没有 autopilot 参与。
每轮交替顺序；驱动内置前提断言：`policy.status.auto_apply.active_expert` 必须等于本轮声称的 expert，
否则该 run 标 invalid（否则可能"同一个 expert 跑了两遍"）。

## 3. 过载区间（60k rps + 16 spinner）：差距存在但不可分辨

| rep | latency-balanced goodput / p50 / p99 | safe-basic goodput / p50 / p99 |
|---|---|---|
| 1 | 43686 / 3.00 / 31.64 | 51406 / 2.26 / 18.16 |
| 2 | 54839 / 1.64 / 16.70 | 31850 / 4.70 / 36.31 |
| 3 | 54269 / 1.88 / 14.99 | 19536 / **14.36** / 45.78 |
| 4 | 10859 / 16.73 / 49.37 | 34882 / 4.32 / 33.46 |
| 5 | 47951 / 2.74 / 22.62 | 46650 / 2.56 / 39.85 |
| 6 | 42489 / 3.21 / 25.55 | 22238 / 12.56 / 48.30 |

配对（latency-balanced vs safe-basic，n=6，10000 次 bootstrap）：
goodput **+37.5% [−41.9, +134.4]**、p99 −45.2% [−60.6, +60.9]、mean −39.8% [−76.4, +113.5]、
over-5ms 份额 −31.4% [−83.7, +92.5]。**全部跨 0，逐轮符号翻转**。
原因是工作点本身不稳：同一臂的 p50 在 2.3ms 与 14.4ms 之间跳（最大在途 1159–3001），
机器在"跟得上"和"队列塌"两个状态之间二选一。**在这个区间里专家差不可测**，
不是"专家没差别"的证据，而是"这个注入强度没有稳定的对照"。

## 4. 稳定区间（40k rps + 8 spinner）：专家差是 0.00%

12 个 run 全部落在稳定状态：两个臂 goodput 都是 **39997–39999**（offered 40000 的 100%），
p50 0.12–0.15ms、p99 1.11–1.29ms、over-5ms 份额 0.00–0.01%。

| 指标 | latency-balanced vs safe-basic（n=6，bootstrap 95%） |
|---|---|
| goodput@5ms | **−0.00% [−0.01, 0.00]** |
| p99 | +2.23% [−3.71, +7.27] |
| p99.9 | +0.75% [−2.93, +8.07] |
| mean latency | +2.32% [−2.86, +10.02] |

**这就是能分辨的区间，答案是"两个 expert 在服务有富余时完全等价"。** 把 40s 延迟代进去：
39999 rps × (−0.00%…−0.01%) × 40s ⇒ **约 0–30 个请求**，即测量上为零。
`GAP_RESOLVED=no`（差值本身与 0 不可区分），所以这个"30 个请求"只能作为上界读，不能当点估计。

## 5. 结论

1. **门的 40s 延迟，在唯一可分辨的工作点上，代价是零**（专家差 ≤0.01% goodput）。
   这与门控实验里"goodput 差异测不出来"是同一件事的两个侧面：不是门便宜，而是**在这个负载下
   换不换 expert 对服务没有影响**。
2. **在专家可能拉开差距的过载区，现有的注入设计无法给出对照**（双稳）。要让"过载下该不该切"
   变成可测问题，需要控制队列状态（例如固定在途/准入控制，或按块记录并只在同一状态内配对），
   这超出本轮范围，记为未完成。
3. 因此"门有价值/有害"仍然**没有结论**；但目前可以确定的是：**没有证据表明门控延迟造成了吞吐损失**，
   而且在能测的区间它确定为零。

## 6. 不能声称的

- 不能声称"过载时 expert 没差别"——那是不可分辨，不是零。
- 不能把 §4 的 0.00% 外推到旗舰矩阵的 60k 场景：那里 offered 率本身就贴着服务膝点。
- `GAP_RESOLVED=no` 的判据是"CI 跨 0"；§4 的 CI 窄但包含 0，故按不可分辨处理。
- 单机、单负载（redis GET）、单注入工具；过载区二稳的来源未定位到具体机制。
- 本轮所有 goodput 数字来自修好的探针；此前各证据的时间戳字段虽假，但其 goodput 由探针内部
  单调时钟计算并与逐请求重建一致，故不受影响（见 §1）。
