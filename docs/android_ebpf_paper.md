**基于 eBPF 的 Android 系统异常监测方法研究**

*An eBPF-Based Anomaly Monitoring Method for Android Systems*

屈雷皓

## 摘 要

随着移动终端承载的交互、后台服务和端侧计算任务不断增加，Android
系统在多任务并发和资源竞争条件下仍容易出现卡顿、响应迟缓和运行状态异常等现象。现有工具多面向阶段性调试，难以在较低侵入条件下持续保留异常发生前后的
CPU、内存与 I/O 上下文。

Android 系统卡顿和响应异常通常与 CPU 调度竞争、I/O
等待和内存分配压力等底层因素相关，但现有分析工具多偏向事后 trace
或宏观状态观测，难以在低开销条件下持续保留异常窗口内的细粒度内核证据。针对这一问题，本文提出一种结合
eBPF 与 PSI 的 Android 系统异常监测方法，并实现自研原型
PerfInsight。该方法在真实 Android 设备上加载 eBPF 程序，采集 CPU、I/O
和内存路径中的关键事件；同时在用户态集成 PSI
监测与门控模块，利用资源停顿压力信号筛选值得重点观测的时间窗口，在低压阶段抑制无效日志，在高压阶段保留核心事件证据。本文基于
OnePlus Ace 3 真机开展实验，覆盖空闲、CPU 压力、I/O 压力、CPU+I/O
混合压力、内存压力和三资源联合压力等场景，并结合 top、/proc/pressure 与
dumpsys gfxinfo 进行对照。实验结果表明，PerfInsight
能够在低压状态下保持较小输出，在压力场景下捕获可解释的多源事件变化；重交互同步实验进一步将
3626 帧用户侧数据与系统指标对齐，得到 114 个 Jank 帧和 26 个 Jank
窗口，为 Android
卡顿和异常监测提供了结构化候选证据。本文结论限定为压力窗口识别、Jank
关联分析和候选证据排序，不将当前结果解释为严格因果根因定位。

**关键词：**Android；eBPF；PSI；异常监测；卡顿分析；I/O 延迟

**Index Terms---**Android, eBPF, PSI, anomaly monitoring, Jank analysis,
I/O latency

## Abstract

Android devices increasingly host interactive applications, background
services, and on-device computation. Under multi-tasking and resource
contention, the system may still suffer from Jank, slow response, and
abnormal runtime states. Existing tools are mainly designed for episodic
debugging and are less suitable for continuously preserving CPU, memory,
and I/O context around anomalies with low intrusiveness.

Android Jank and responsiveness anomalies are often related to low-level
factors such as CPU scheduling contention, I/O waiting, and memory
allocation pressure. Existing tools are effective for post-hoc tracing
or coarse-grained state inspection, but they are less suitable for
continuously preserving fine-grained kernel evidence around abnormal
pressure windows with low overhead. To address this issue, this paper
proposes an eBPF- and PSI-based anomaly monitoring method for Android
systems and implements a prototype named PerfInsight. The method loads
eBPF programs on a real Android device to collect key events from CPU,
I/O, and memory paths, while integrating a PSI monitoring and gating
module in user space to identify pressure windows. It suppresses
redundant logs under low pressure and retains core event evidence when
system pressure increases. Experiments on OnePlus Ace 3 cover idle, CPU
pressure, I/O pressure, CPU+I/O mixed pressure, memory pressure, and
combined CPU+I/O+memory pressure scenarios, with top, /proc/pressure,
and dumpsys gfxinfo used for comparison. Results show that PerfInsight
keeps output small in low-pressure states and captures interpretable
multi-source event changes under pressure. A synchronized
heavy-interaction experiment further aligns 3,626 user-side frames with
system metrics, obtaining 114 Jank frames over 26 Jank windows and
providing structured candidate evidence for Android Jank and
responsiveness anomaly monitoring. The conclusions are limited to
pressure-window identification, Jank association analysis, and candidate
evidence ranking, rather than strict causal root-cause localization.

# I. 引言

Android
设备已从单纯的移动交互终端演化为承载游戏渲染、在线协作、多媒体处理、后台同步以及端侧智能任务的复杂计算平台。随着终端硬件性能提升和应用生态持续扩张，移动系统中同时运行的前台交互线程、后台服务、系统守护进程和厂商增强组件不断增多，资源竞争关系也随之变得更加复杂。已有研究和
Android 平台文档均指出，用户可感知的卡顿、响应迟缓和 Jank 往往与 CPU
竞争、I/O 等待、内存压力、系统 jitter
以及帧完成信号缺失等因素相关^\[1\]\[2\]\[3\]^。因此，Android
异常问题往往不是单一资源占用率升高造成的，而是 CPU 调度、内存管理、块
I/O
路径和后台服务竞争共同作用的结果。此类问题具有瞬时性、跨层传播和难以稳定复现等特点，异常发生后再启动分析工具往往已经错过关键上下文，也难以还原异常出现前资源压力逐步累积的过程。

从用户体验角度看，Android
异常通常首先表现为界面滑动不连续、输入反馈变慢、应用启动时间增加或后台任务影响前台交互。然而，从系统实现角度看，这些现象并不直接等同于某一个单独指标超过阈值。一个短时间的
I/O
请求排队可能导致关键线程进入不可运行状态，一次内存回收可能延长系统服务响应路径，频繁迁核可能带来缓存局部性下降，而后台同步、日志写入或厂商服务活动也可能在短时间内放大资源竞争。更复杂的是，这些因素之间并非相互独立：I/O
阻塞可能导致线程睡眠和唤醒延迟，内存压力可能触发回收和写回，CPU
竞争又会影响用户态守护进程和系统服务处理事件的及时性。因此，面向 Android
的异常监测需要从多维底层行为中保留证据，而不是仅观察单次 CPU
占用率、内存剩余量或某条应用日志。

现有 Android 性能分析工具为问题定位提供了重要基础。Android 官方文档将
Perfetto、Android Studio Profiler、system tracing、simpleperf 和 Android
Vitals 等工具作为性能检查的重要入口，Perfetto 也提供 Frame Timeline 与
Android trace analysis
等数据源用于帧时间线和系统调度分析^\[4\]\[5\]\[6\]^。这些工具在人工复现、短时间采样和专家离线分析中非常有效，也是
Android
工程实践中最常见的诊断手段。但是，面向持续异常监测时，它们仍存在三方面不足。首先，许多工具依赖人工触发或预先配置，异常发生后再启动采集容易错过前序状态；其次，完整
trace
通常数据量较大，长期常驻会带来存储和分析负担；最后，不同工具输出粒度和语义差异较大，CPU、内存、I/O
与应用状态之间缺少统一的关联方式。

因此，本文关注的问题不是如何替代现有调试工具，而是如何在真实 Android
设备上构建一种更适合在线监测的底层观测机制。这样的机制应满足几个基本要求：一是低侵入性，即尽量避免修改
Android
Framework、应用代码或内核源码；二是持续性，即能够在设备运行过程中保留异常前后的关键上下文；三是多维性，即同时覆盖调度、内存分配与
I/O
等关键路径事件；四是可关联性，即不同来源的数据应能通过时间、进程、线程和
CPU
上下文进行统一组织；五是可解释性，即输出结果不仅能说明系统处于压力状态，还能进一步指向压力可能来自哪类底层行为。

eBPF 的发展为上述需求提供了可行路径。作为 Linux
内核中的安全可编程观测机制，eBPF
允许开发者在验证器约束下将小型程序挂载到 tracepoint、kprobe
等内核事件点，从而在不重编译内核的前提下获取关键路径信息。BPF
性能工具、Linux 内核验证器文档、AOSP eBPF 机制和 libbpf
文档共同说明，eBPF
已经成为系统观测、性能分析和平台级监控的重要基础^\[7\]\[8\]\[9\]\[10\]^。对于
Android 设备而言，GKI、BTF 和 CO-RE 等机制逐步完善后，研究者可以利用
libbpf 生态在 PC 端开发并交叉编译到 ARM64
设备上运行。这种方式既保留了内核态观测的细粒度优势，又避免了传统内核模块部署风险较高、适配成本较大的问题。

然而，仅有 eBPF
采集能力并不足以形成适合长期运行的异常监测系统。在原型初期，若直接让多个探针持续输出细粒度日志，空闲和轻负载阶段也会产生大量无效事件，既增加存储与解析负担，也可能削弱系统在线运行的可持续性。这一现象说明，Android
异常监测不能只依赖"尽可能多地采集"，还需要先判断系统是否进入值得重点观察的压力窗口。为此，本文在自研原型
PerfInsight 中实现 PSI 监测与门控模块，将 PSI（Pressure Stall
Information）作为资源停顿压力指标和核心采集触发依据。PSI 由 Linux
社区提出并在内核文档中定义为用于度量 CPU、内存和 I/O
停顿压力的机制，其关注点是任务因资源竞争而无法推进的时间比例^\[11\]\[12\]^。相比单纯的
CPU 利用率、剩余内存或 I/O 吞吐，PSI 更接近 Android
卡顿问题中的底层资源竞争机制：关键线程是否因为资源压力而无法及时获得执行机会。

需要强调的是，PSI 并不直接等同于用户感知卡顿。界面 Jank
还受到前台应用渲染负载、系统调度策略和交互路径等因素影响，因此本文不把
PSI
写成唯一卡顿标签，而是将其定位为潜在卡顿窗口的筛选信号。后续真机实验表明，这一定位是可验证的：空闲场景下，PerfInsight
内部的 PSI
门控模块能够显著抑制无效日志输出；CPU、内存和多资源压力升高时，该模块触发已经挂载的
eBPF 采集程序输出更丰富的调度、I/O 和内存分配证据；逐秒 gfxinfo
同步实验则进一步显示，系统侧 PSI
指标可以与用户侧帧耗时标签进入同一时间窗口，为后续滞后相关和卡顿证据分析提供基础。

基于这一认识，本文提出一种结合 eBPF 与 PSI 的 Android
系统异常监测方法。系统在用户态集成 PSI 监测与门控模块，并加载 eBPF
程序挂载到调度、块 I/O 和内存相关内核事件点。运行过程中，PSI
模块首先筛选资源停顿和潜在卡顿窗口，在低压状态下保持较少输出；当压力达到设定阈值后，再驱动已挂载的
eBPF 采集模块输出更细粒度事件。采集内容覆盖 CPU
runtime、调度分派、任务抢占、跨核迁移、块 I/O
排队与执行延迟、伙伴系统状态等信息，并由用户态程序统一接收和保存。离线阶段进一步将原始日志解析为
CSV、图表和实验摘要，使监测结果能够服务论文分析、候选证据排序和后续因果验证。

本文的研究边界需要特别说明。当前工作并不声称已经实现完整的自动根因诊断系统，也不将端侧智能模型推理作为主要结论。相反，本文把目标收束为"异常监测与证据保留"：即系统是否能够在真实设备上稳定运行，是否能在不同压力场景下捕获可区分的底层事件变化，是否能通过结构化数据为后续卡顿分析提供可靠输入。这样的定位更加符合现阶段实验条件，也能避免将尚未充分验证的智能诊断能力写成过强结论。

为了验证方法可行性，本文在 OnePlus Ace 3
真机上完成实验，并将自研监测原型命名为 PerfInsight。实验覆盖空闲、CPU
压力、I/O 压力、CPU+I/O
混合压力、内存压力和三资源联合压力等场景，并分别使用
PerfInsight、top、/proc/pressure 和 dumpsys gfxinfo
进行对照。实验结果表明，PSI 在 PerfInsight 中具有双重作用：一方面，PSI
模块能够作为资源停顿压力观测单元，标记 CPU、内存和 I/O
压力影响任务推进的时间窗口；另一方面，它能够作为潜在卡顿窗口筛选和采集门控单元，控制已挂载
eBPF 采集程序在压力升高后输出 runtime、调度、buddy 与 I/O
延迟等细粒度证据。进一步的逐秒同步实验表明，系统侧 PSI 指标可以与
gfxinfo 帧耗时标签对齐，从而为后续面向用户侧卡顿的滞后分析提供基础。

**本文主要贡献包括：**1）提出一种面向 Android 系统异常监测的 eBPF 与 PSI
联合观测方法，将 PSI 监测与门控模块集成到自研原型中，并与挂载在调度、块
I/O 和内存事件点上的 eBPF 采集程序形成联动；2）实现一套可在真实 Android
设备上运行的原型，覆盖调度、I/O
延迟、运行时和资源压力等关键证据；3）构建自动化实验与离线解析流程，能够保存
run 元数据、生成结构化 CSV 和论文图表；4）基于 OnePlus Ace 3
完成多压力场景实验，并与 top、/proc/pressure、dumpsys gfxinfo
等工具进行对照，验证 PSI
模块在低压抑制和高压触发中的有效性；5）在实验数据基础上采用窗口特征、异常偏离度、逐秒
gfxinfo 标签和压力状态识别模型进行候选证据排序，给出面向 Jank
窗口的关联分析结果，为后续更严格的卡顿归因和因果验证提供依据。

本文其余部分安排如下。第二部分介绍 Android 卡顿、eBPF 和 PSI
的背景及设计动机；第三部分描述系统总体架构、事件采集和 PSI
门控机制；第四部分说明原型实现与实验自动化流程；第五部分基于真机实验数据评估方法效果，并给出候选证据排序；第六部分讨论相关工作；第七部分总结全文并展望后续研究。

# II. 背景与动机

## A. Android 卡顿与资源竞争

Android
卡顿本质上是交互相关任务未能在用户期望的时间窗口内完成。对于普通界面渲染，系统需要在固定刷新周期内完成输入分发、主线程处理、RenderThread
渲染、SurfaceFlinger 合成以及显示提交等步骤；在 60 Hz
场景下，单帧预算通常约为 16.67
ms，高刷新率设备还会进一步压缩这一时间窗口。若应用或系统在某一帧内无法完成必要工作，Choreographer
可能丢弃该帧，用户就会感知到滑动不连续、动画跳变或点击反馈变慢。Android
Vitals 也将慢帧、冻结帧和 ANR
作为不同层次的响应性问题，其中冻结帧通常代表更严重的长时间无响应状态^\[3\]^。

从执行链路看，卡顿并不只发生在应用 UI
代码内部。一次看似简单的滑动可能经过输入事件分发、主线程消息队列、布局与绘制、渲染线程、Binder
调用、GPU
合成和系统服务调度等多个阶段。任何阶段出现等待都可能向用户侧表现为帧耗时升高。例如，UI
线程被后台任务抢占会延迟布局计算，RenderThread 等待 CPU 或 GPU
资源会影响绘制提交，SurfaceFlinger
或系统服务阻塞会影响合成与显示，存储请求排队则可能使关键线程在 I/O
路径上进入睡眠。由于这些阶段跨越应用层、Framework、系统服务和内核调度路径，仅依赖单一应用日志很难还原完整链路。

已有 Android
响应性研究也表明，用户可感知的卡顿和慢响应往往具有多来源特征。MobiCom
2024 关于移动进程管理的大规模研究指出，慢 UI
响应在真实设备上普遍存在，并且大量事件与系统级资源竞争、后台常驻或资源占用型应用有关^\[1\]^；TMC
2024 关于 Android 响应性的研究则进一步区分了 slow rendering、frozen
frame、ANR 和 SNR 等不同现象，指出冗余 UI 渲染、I/O
相关机制和系统服务阻塞都可能造成响应性下降^\[2\]^。这些研究说明，卡顿问题不能简单归结为某一个应用"写得慢"，也不能仅用硬件性能或平均
CPU 利用率解释。

资源竞争是 Android 卡顿分析中最常见也最难直接观测的因素之一。CPU
侧，前台线程可能因运行队列变长、优先级竞争、抢占或频繁迁核而错过帧预算；内存侧，页面分配、回收、压缩、文件页写回或低内存管理可能拉长系统调用和服务响应路径，Android
的 LMKD
机制也说明平台会根据内存压力和进程优先级对低内存状态进行系统级处理^\[13\]^；I/O
侧，块设备请求排队、同步写入、日志落盘和后台下载可能让关键线程等待存储完成；网络侧，实时通信或游戏流量还可能受到后台下载、QUIC
流量或其他非实时任务影响。更复杂的是，这些因素往往相互耦合：内存压力可能触发回收和写回，I/O
阻塞可能导致线程睡眠与唤醒延迟，CPU
竞争又会影响用户态守护进程、系统服务和应用主线程处理事件的及时性。

因此，面向 Android
的异常监测需要同时关注用户侧表现和系统侧证据。用户侧的 \`dumpsys
gfxinfo\`、FrameTimeline 或 Perfetto
能说明某一时间段是否出现帧耗时异常，但它们并不必然解释异常来自 CPU
调度、I/O 路径还是内存分配；系统侧的 CPU 使用率、内存剩余量和 I/O
吞吐又只能提供宏观背景，容易遗漏关键线程等待和资源停顿。本文在原型中集成
PSI 监测模块，是因为 PSI
直接描述任务因资源竞争而无法推进的时间比例，适合用于筛选潜在压力窗口；再结合
eBPF 对调度、I/O
和内存路径的细粒度采集，才能把"是否出现压力"进一步转化为"压力可能来自哪些底层机制"的可解释证据。

## B. Android 上的 eBPF

eBPF 是 Linux 内核提供的一种安全可验证的内核扩展机制。开发者可以将受限的
eBPF 程序挂载到 tracepoint、kprobe、perf event、cgroup
或网络路径等内核事件上，在不修改内核源码、不重新编译内核模块的情况下采集运行时状态。对于性能观测而言，eBPF
的价值不在于替代 Perfetto、simpleperf
或日志系统，而在于能够在事件发生的内核路径上直接记录上下文，例如调度切换、任务唤醒、块
I/O
请求、运行时统计和资源分配状态。这种事件级观测能力使其适合补充传统工具难以覆盖的细粒度内核证据。

与传统内核模块相比，eBPF
更适合移动端异常监测的一个关键原因是其安全边界更加明确。eBPF
程序加载前需要经过内核验证器检查，验证过程会分析控制流、寄存器状态、栈访问、指针边界和辅助函数调用合法性，从而降低非法内存访问或不受控执行对内核稳定性的影响^\[8\]^。虽然验证器约束会限制程序复杂度，例如不能任意访问内核内存、不能执行不受控循环、需要显式处理
map 和 ring buffer
访问边界，但这些限制反而使研究型监测原型更容易形成可审查、可复现的内核侧采集逻辑。

Android 对 eBPF 的支持具有其自身特点。AOSP 文档指出，Android 系统包含
eBPF loader 和相关库，系统启动时可以加载位于 \`/system/etc/bpf/\` 的
eBPF 对象，并将程序和 map 固定到 BPF 文件系统中，以便用户态组件读取 map
或附加
tracepoint^\[9\]^。这一机制最初主要服务于系统网络、统计和平台级监控能力，但它也说明较新
Android 设备已经具备运行 eBPF 程序的基础设施。随着 Android GKI、BTF
以及稳定内核接口的发展，eBPF
程序在不同设备和内核版本之间的适配成本逐步降低，为面向真机的系统观测研究提供了条件。

不过，Android 上使用 eBPF 仍然不同于普通服务器 Linux
环境。首先，生产设备通常受到 SELinux、系统分区只读、Bootloader
锁定和权限模型限制，研究原型往往需要 root
权限或解锁设备才能加载自定义程序。其次，Android 内核配置、厂商裁剪、BTF
可用性和符号暴露程度会影响 CO-RE
程序能否稳定运行。再次，移动设备的功耗、温控和前后台调度策略更敏感，监测程序本身如果持续输出大量日志，也可能改变被观测系统的状态。因此，在
Android 场景中，eBPF
采集不应追求"越多越全"，而应围绕异常问题选择关键事件，并通过门控、缓冲和离线解析控制观测开销。

本文采用 libbpf-bootstrap 作为原型基础，是因为 libbpf 能够完成 BPF
对象加载、重定位、验证和挂载等重复工作，使用户态程序将主要精力集中在采集逻辑与数据组织上^\[10\]\[14\]^。具体到本文场景，PerfInsight
通过用户态程序加载多个 eBPF 采集模块，并使用 ringbuf
将内核侧事件传递到用户态日志。采集目标围绕 Android
卡顿和资源竞争证据展开，包括调度运行时间、任务分派、抢占迁移、块 I/O
延迟和内存分配状态等。这样的设计既利用了 eBPF
在内核路径上的低侵入观测能力，也保留了用户态脚本统一管理实验、保存元数据和生成论文图表的灵活性。

## C. PSI 压力信号

Pressure Stall Information（PSI）是 Linux
内核用于度量资源停顿压力的机制。传统资源指标通常描述"资源是否被使用"，例如
CPU 利用率、内存剩余量或 I/O 吞吐；PSI
则更关注"任务是否因为资源竞争而无法继续推进"。当 CPU、内存或 I/O
资源发生竞争时，任务可能进入等待状态，进而造成延迟尖峰、吞吐下降甚至 OOM
等问题。Linux 内核文档指出，PSI
的目标正是识别并量化这类资源紧张对工作负载造成的时间影响^\[12\]^。因此，PSI
与本文关注的 Android 卡顿和异常监测问题天然相关。

在接口形式上，PSI 通过 \`/proc/pressure/cpu\`、\`/proc/pressure/memory\`
和 \`/proc/pressure/io\` 暴露 CPU、内存和 I/O
三类压力信息。每类资源通常包含 \`some\` 和 \`full\` 两种状态：\`some\`
表示至少有部分任务因该资源停顿，\`full\`
表示所有非空闲任务同时因该资源停顿。二者进一步以
\`avg10\`、\`avg60\`、\`avg300\` 表示最近 10 秒、60 秒和 300
秒窗口内的停顿比例，并通过 \`total\` 记录累计停顿时间^\[12\]^。其中
\`avg10\`
对短时异常更敏感，适合作为交互式系统中的近实时压力指示；\`avg60\` 和
\`avg300\` 更适合观察中长期趋势。

PSI 相比平均利用率更适合用于 Android 卡顿分析。平均 CPU
利用率较高并不一定意味着用户可感知卡顿，因为系统可能仍在有效执行任务；相反，即使
CPU 利用率并不极端，关键线程也可能因为运行队列、内存回收或 I/O
等待而错过帧预算。内存和 I/O
场景同样如此：剩余内存较低不一定立即造成卡顿，但直接回收、页面写回或文件系统同步可能使前台线程在关键路径上停顿；I/O
吞吐较高也不等同于异常，真正影响交互体验的是请求排队和同步等待是否阻塞了关键任务。PSI
通过记录"停顿时间占比"弥补了这些宏观指标的不足，使其能够更接近资源竞争对任务推进造成的直接影响。

本文将 PSI
定位为资源停顿压力指标、潜在卡顿窗口筛选信号和细粒度采集门控依据。早期原型如果持续输出所有
eBPF 事件，会产生大量与异常无关的日志，并可能引入额外 I/O 开销；将 PSI
监测逻辑作为 PerfInsight
的独立模块集成后，系统可以先以较低成本观察资源压力，再在压力超过阈值时触发更详细的调度、I/O
和内存事件保存。具体而言，PerfInsight 默认采用 \`avg10\`
窗口和阈值触发方式：当 PSI 低于阈值时，程序仅保留轻量门控状态；当
CPU、内存或 I/O 停顿压力升高时，门控模块驱动已挂载的 eBPF
采集程序进入核心采集阶段，记录 runtime、调度迁移、块 I/O 延迟、buddy
状态等证据。这样的设计使系统既具有长期在线监测潜力，也避免在低压状态下被无效日志淹没。

需要说明的是，PSI 不是用户感知卡顿的唯一标签，也不等同于 \`dumpsys
gfxinfo\` 或 Perfetto
中的帧耗时结果。它描述的是资源竞争导致任务停顿的系统侧状态，而用户侧卡顿还受到前台应用逻辑、界面复杂度、渲染线程、GPU
合成和输入路径等因素影响。因此，本文并不将 PSI
单独作为卡顿判定器，而是将其作为异常窗口的先验筛选信号：PSI
指示"系统是否正在经历足以影响任务推进的资源停顿"，eBPF
进一步回答"停顿窗口内哪些内核路径发生了异常变化"，用户侧帧耗时数据则用于后续验证这些系统侧证据是否与实际交互卡顿对齐。

## D. 设计动机

综上所述，Android
卡顿和异常监测面临的核心困难并不是缺少单个观测指标，而是缺少能够把用户侧现象、系统压力状态和内核路径证据连接起来的轻量化方法。用户侧工具可以指出某一时间段存在慢帧或冻结帧，却难以直接解释底层资源竞争来自
CPU、I/O 还是内存路径；系统监控工具可以提供 CPU 利用率、空闲内存和 I/O
吞吐等宏观状态，却容易遗漏关键线程等待、调度迁移和请求排队等细粒度原因；内核级
tracing
可以捕获丰富事件，但如果不加筛选地持续采集，又会带来日志量、运行开销和离线分析复杂度问题。

因此，本文的设计动机首先来自对单一工具局限性的观察。仅依赖 \`top\` 或
\`/proc/pressure\`
这类系统接口，能够判断设备是否处于高负载或资源停顿状态，但无法保存足够的事件上下文；仅依赖
\`dumpsys gfxinfo\` 或
Perfetto，能够观察帧耗时和交互表现，但无法直接定位内核路径中的调度、I/O
或分配异常；仅依赖 eBPF
全量采集，又会在低压状态下产生大量与异常无关的数据，影响长期在线监测可行性。本文试图在这些工具之间建立互补关系，而不是简单替代其中任何一种。

基于上述考虑，本文将 PSI 模块与 eBPF 采集模块组合起来使用：PSI
模块负责以较低成本识别资源停顿压力窗口，eBPF
程序负责在压力窗口内保存细粒度内核证据。二者的结合形成了一个分层观测思路：第一层由
PerfInsight 内部 PSI
模块判断系统是否存在足以影响任务推进的压力；第二层在压力升高时触发挂载在调度、运行时、I/O
延迟和内存分配相关事件点上的 eBPF
程序输出数据；第三层由用户态程序和离线脚本将事件组织为可分析数据，并与
top、gfxinfo 等工具结果进行对照。这种设计既保留了 eBPF
的细粒度优势，也避免在所有时间段持续输出高成本日志。

本文原型 PerfInsight
的目标不是构建一个封闭的性能分析工具，而是验证一种面向 Android
真机的异常监测路径是否成立。为此，系统需要满足三个要求：其一，能够在真实
Android 设备上运行，而不是仅在模拟器或桌面 Linux
上验证；其二，能够覆盖与卡顿和资源竞争相关的关键内核路径，而不是停留在单一
CPU 或 I/O 指标；其三，能够把每轮实验的原始日志、元数据、结构化 CSV
和论文图表保存下来，使实验结果具备可追溯性和可复核性。

同时，本文对研究边界作出有意收束。当前工作不声称已经实现完整的自动根因诊断，也不将
PSI
或机器学习模型作为用户感知卡顿的直接判定器。本文更关注异常监测与证据保留这一前置环节，即系统是否能够在压力出现时捕获可区分的底层事件变化，是否能够在低压状态下抑制无效采集，是否能够为后续滞后相关分析、可解释模型和因果验证提供结构化输入。这样的定位使后续实验结论能够建立在可观测数据之上，而不是过早夸大为端到端卡顿诊断能力。

# III. 系统设计

## A. 总体架构

PerfInsight
的总体架构围绕"压力感知、事件采集、日志组织和证据分析"四个环节展开，如图1所示。系统并不把
eBPF 采集、PSI
监测和离线分析视为相互独立的工具集合，而是将其组织为一个分层观测链路：Android
内核层提供 PSI 压力信号以及 CPU、I/O、内存三类内核事件来源；PerfInsight
用户态运行层负责 eBPF 程序加载、PSI
门控决策、事件接收和模块化日志输出；离线处理层再将原始日志转换为结构化数据，用于后续压力状态识别、Jank
关联分析和候选证据排序。这样的分层设计使系统既能够保留内核事件的细粒度信息，也能够避免把实验分析流程直接混入在线采集路径。

在启动阶段，PerfInsight 通过用户态加载与挂载模块完成 eBPF
对象加载、验证、探针挂载以及 map、perf buffer 或 ringbuf
等通信结构初始化。该阶段属于控制和初始化过程，不构成运行时事件数据流。完成初始化后，CPU
侧采集关注调度、运行时和抢占等执行路径，I/O
侧采集关注请求下发、完成和延迟变化，内存侧采集关注分配、回收和 buddy
等状态变化。三类采集逻辑在内核侧形成已挂载的 eBPF
探针集合，为后续压力窗口内的证据保留提供事件来源。

在运行阶段，系统同时存在两条不同方向的关系。第一条是事件数据流，即内核侧
eBPF
探针在事件发生时将采集结果上报到用户态事件接收模块，随后由模块化日志输出组件按
CPU、I/O、内存和门控状态等类别保存。第二条是 PSI 门控流，即 PerfInsight
内部的 PSI
感知逻辑根据系统压力状态判断当前是否处于值得重点观察的窗口。低压状态下，系统主要保留轻量门控状态，从而抑制大量无效核心日志；压力升高后，系统保留更细粒度的
eBPF 事件和上下文信息。需要强调的是，eBPF
探针并不是在高压后才动态挂载，压力门控影响的是核心事件的提交、保留和日志输出策略。

该架构的关键在于将"是否需要重点观测"和"观测到什么事件"分离处理。PSI
提供资源停顿压力的系统侧信号，用于筛选潜在异常窗口；eBPF 负责在 CPU、I/O
和内存路径上捕获细粒度事件，用于解释压力窗口内可能出现的执行延迟、请求等待和分配活动；用户态日志模块负责把多源事件组织为可追溯的原始证据；离线脚本进一步完成日志解析、窗口构造和结构化统计。通过这种链路，本文方法能够从连续运行的底层事件中筛选出更有分析价值的压力阶段，并为第五部分的实验评估和候选证据排序提供统一数据基础。

## B. 多源事件采集

多源事件采集模块的设计目标不是尽可能覆盖所有内核事件，而是围绕 Android
卡顿和系统异常中最常见的资源竞争路径保留关键证据。本文将采集对象划分为
CPU、I/O 和内存三类：CPU 事件反映任务是否能够及时获得执行机会，I/O
事件反映请求是否在存储路径上发生排队或执行延迟，内存事件反映分配、回收和
buddy
状态是否出现明显波动。三类事件分别对应调度竞争、存储等待和内存分配压力三种候选机制，能够与
PSI 压力信号和用户侧帧耗时结果形成互补。

CPU
侧采集主要关注任务运行时间、调度切换、调度分派、抢占和跨核迁移等事件。Android
前台交互通常依赖 UI 线程、RenderThread、系统服务和 Binder
调用链的及时推进；当系统处于 CPU
竞争或多任务争抢状态时，关键线程可能经历更长的等待、更频繁的抢占或迁移，从而增加帧生成和响应路径的不确定性。因此，PerfInsight
在 CPU 侧保留 runtime、调度延迟、抢占关系和迁核信息，不把 CPU
利用率作为唯一依据，而是进一步记录任务在调度路径中的实际执行和等待状态。

I/O
侧采集围绕块请求的下发、排队、完成和延迟展开。移动设备中的应用启动、资源加载、日志写入、数据库访问和后台下载都可能引起
I/O
活动，但只有当请求排队时间、执行时间或总延迟升高时，才更可能影响上层任务推进。PerfInsight
因此不只记录 I/O
次数，而是将请求生命周期中的关键时间点和延迟字段保存下来，使后续分析能够区分"存在
I/O 活动"和"存在 I/O 等待证据"。这一设计也解释了本文实验中纯 I/O
场景需要谨慎讨论：I/O
压力是否形成强触发，与设备即时状态、请求模式和门控阈值有关。

内存侧采集主要关注分配路径和 buddy 状态。Android
系统在多应用切换、重应用启动或后台服务并发运行时，内存分配和回收压力可能导致任务等待、页面回收或缓存扰动。相比单纯记录剩余内存大小，buddy、分配状态和相关上下文更能反映内存子系统内部是否进入活跃调整阶段。本文将内存侧证据与
CPU、I/O
证据并列，是因为实际卡顿往往并非单一资源造成，强内存压力可能同时牵引调度活动和
I/O 等待，三资源联合场景也可能呈现非线性叠加关系。

为保证不同来源的事件能够在离线阶段关联，用户态日志在保存事件值的同时保留进程名、PID、CPU
编号、时间戳或时间相关字段等上下文信息。这些字段本身不直接构成根因判断，但能够把分散的调度、I/O
和内存事件放入同一时间窗口与同一运行场景中比较。换言之，多源事件采集提供的是候选证据集合，而不是单条规则化结论；后续的数据处理层需要对这些日志进行窗口化和统计化，才能进一步支持压力状态识别、Jank
窗口关联和候选证据排序。

## C. PSI 门控监测

PSI 门控监测模块用于解决细粒度 eBPF
采集在长期运行中的日志膨胀问题。若所有调度、I/O
和内存事件都在任意负载下持续输出，系统在空闲或轻负载阶段也会产生大量与异常无关的日志，既增加设备侧
I/O 开销，也会降低离线分析效率。PSI 描述任务因 CPU、内存或 I/O
资源竞争而无法推进的压力状态，能够比单纯 CPU 利用率、剩余内存或 I/O
次数更直接地反映任务是否受到资源停顿影响。因此，PerfInsight 将 PSI
作为潜在异常窗口的筛选信号，用于决定哪些时间段需要保留更完整的内核事件证据。

从运行流程看，eBPF 探针在程序启动阶段已经完成加载和挂载，PSI
门控并不是在高压后再动态启动探针。运行时，系统持续监测压力信号，并根据资源类型、统计窗口和阈值判断当前是否进入压力窗口。当压力不足时，PerfInsight
主要记录轻量门控状态，并抑制核心事件日志输出；当压力升高且表明任务推进可能受到资源竞争影响时，系统保留调度、I/O
和内存路径上的关键事件。这样的设计把"事件是否发生"和"事件是否值得保存"分开处理，使内核侧观测能力与在线运行开销之间形成折中。

结合当前原型源码，PSI
门控在实现上包含内核态和用户态两类路径。对于整合程序，内核侧 eBPF
逻辑会根据 PSI 判断结果维护门控标志，部分调度事件在提交到 ringbuf
前即可被过滤；对于其他独立采集模块，eBPF
程序同样预先挂载并持续接收事件，但用户态回调会根据 PSI
触发标志决定是否打印或写入日志。因此，本文在架构描述中将其概括为"高压窗口下保留核心事件和日志输出"，而不是写成"高压后开启采集模块"。这种表述更符合实际实现，也能避免把加载挂载关系误解为运行时数据流。

需要进一步说明的是，PSI 门控不是用户感知卡顿的直接标签。PSI
只能说明系统层面存在资源停顿压力，而用户侧 Jank
还受到前台应用逻辑、渲染负载、输入路径和系统策略等因素影响。本文将 PSI
定位为先验筛选信号和采集门控依据：它负责指出值得重点观察的压力窗口，eBPF
事件负责提供窗口内的 CPU、I/O
和内存证据，用户侧帧耗时数据则用于后续关联验证。由此，PSI
门控模块的贡献不在于单独判断卡顿，而在于降低无效采集、增强异常阶段证据密度，并为后续候选证据排序提供更清晰的数据边界。

## D. 数据组织

数据组织模块负责将在线采集得到的事件转换为后续可复核、可统计和可写入论文的证据材料。由于
PerfInsight 同时包含 PSI 门控状态、CPU 调度事件、I/O
延迟事件和内存分配相关事件，如果所有输出混合在同一日志中，不仅会增加解析难度，也会削弱不同证据来源之间的边界。因此，系统在用户态按模块保存日志，将门控状态、runtime、I/O、buddy、抢占和迁核等信息分别落盘，使每类证据都能独立统计，同时又能在离线阶段按照时间和
run 信息重新对齐。

每次实验运行均被组织为独立 run。实验脚本在启动监测程序前创建 run
目录，并记录设备型号、Android
版本、内核版本、实验场景、压力类型、运行时长、启动时间、程序二进制版本、配置文件和采集参数等元数据。这些元数据的作用不只是描述实验环境，更重要的是为后续结果解释提供上下文。例如，同样是
I/O
场景，不同轮次的触发强度可能受到设备即时状态和压力负载形态影响；如果缺少
run
级元数据，就难以判断某一组日志规模或延迟指标来自正式实验、脚本调试还是异常中断样本。

离线解析阶段采用"原始日志---结构化
CSV---窗口化指标"的处理方式。解析脚本首先对各模块日志进行流式读取，提取事件数量、延迟分布、P95、日志规模和
PSI/top/gfxinfo 等同步字段；随后生成 run
级摘要、模块级摘要和一秒窗口数据。run
级摘要用于比较不同压力场景的整体响应，模块级摘要用于判断哪些子系统证据更活跃，一秒窗口数据则用于后续与用户侧帧耗时标签对齐。通过这种层次化组织，原始日志既不会被直接丢弃，也不会直接作为论文结论，而是被转换为可统计、可追溯的中间数据。

为保证数据集边界清晰，本文在离线阶段只统计正式 run 白名单，排除
dryrun、脚本修复、参数试探和异常中断样本。这样做可以避免把调试过程中的偶然输出混入论文结果，也使第五部分中的均值、范围、P95
和候选证据排序都有明确来源。需要指出的是，本文当前的数据组织方式仍以文件系统、CSV
和 Markdown/Word
报告为主，没有把数据库作为唯一数据源；这种方式更便于保留原始证据和复现实验链路。后续如需扩展到更大规模采集，可以在保持原始
run 目录和 CSV 不变的前提下增加数据库索引或批量分析接口。

# IV. 原型实现

## A. 原型环境

本文原型在真实 Android 设备 OnePlus Ace 3
上完成实现与验证。选择真机环境而不是仅在桌面 Linux 或 Android
模拟器中验证，是因为移动端卡顿和资源竞争与设备内核版本、调度策略、存储路径、内存管理、前后台应用状态以及厂商系统配置密切相关。桌面
Linux 能够验证 eBPF 程序的基本挂载和事件输出，但难以复现 Android
真机中的应用交互、后台服务、系统守护进程和移动端资源管理行为。因此，本文将真机运行作为原型可行性的必要条件。

实验设备具备 Root 权限，Android 版本为 16，内核为 Linux 5.15.180 Android
GKI。该环境能够提供本文原型所需的 eBPF、BTF 和 PSI 相关能力：eBPF
用于挂载调度、I/O 和内存相关事件点，BTF
用于降低内核结构访问和版本适配难度，PSI 用于获取资源停顿压力信号。Root
权限主要用于加载和运行自定义 eBPF
程序、访问相关内核接口以及在设备侧保存实验日志。需要说明的是，Root
环境是研究原型验证所需的实验条件，并不意味着本文方法已经完成普通量产设备上的无权限部署；本文参考
Android 侧 libbpf-bootstrap
移植工程完成真机交叉编译和部署路径适配^\[15\]^。

原型程序以 Android ARM64 二进制形式部署到设备侧运行目录，并在 root
权限下启动。用户态程序负责读取配置文件、加载 eBPF
skeleton、完成探针挂载、初始化事件缓冲区以及创建模块化日志目录。由于
Android 系统分区通常只读，本文没有依赖将 eBPF
对象安装到系统目录，而是采用实验目录部署方式完成真机验证。该方式便于在不同配置和压力场景下快速替换二进制、保存日志和拉取结果，同时也减少了对系统镜像的长期改动。

PC 侧主要承担交叉编译、ADB
部署、实验脚本调度和离线解析任务。编译阶段生成面向 Android ARM64
的用户态二进制和 eBPF 相关对象；运行阶段通过 ADB
将程序和配置推送到设备，并由脚本控制实验时长、压力场景、日志拉取和元数据记录；离线阶段再在
PC 侧解析原始日志并生成
CSV、图表和论文结果。这样的实现分工使设备侧只承担必要的在线监测与日志输出，而把统计分析和图表生成放到
PC 侧完成，有利于降低真机运行负担并提高实验可复现性。

## B. 用户态程序与运行参数

PerfInsight 的用户态程序是连接内核侧 eBPF
事件和离线实验数据的核心组件。程序启动后首先解析配置文件，根据配置启动不同采集线程，并完成
eBPF skeleton 的打开、加载、验证和挂载。随后，用户态程序初始化 perf
buffer 或 ringbuf 等事件接收通道，在运行过程中接收内核侧上报的 CPU、I/O
和内存相关事件，并根据模块类型写入对应日志。与单独运行某一个 eBPF
示例程序不同，PerfInsight 的用户态部分承担了多模块调度、PSI
门控、事件接收、日志落盘和运行参数管理等多项职责。

本文原型采用配置文件驱动的运行方式。配置文件列出需要启动的采集模块及其参数，主程序读取配置后为每个模块创建独立线程。这样做有两个好处：一方面，可以在不重新编译二进制的情况下调整启用模块、保存选项和门控参数；另一方面，实验脚本能够把配置文件与
run
元数据一起保存，从而保证每轮实验的采集逻辑可追溯。当前实验中主要启用整合采集模块以及调度、I/O、runtime、buddy、抢占和迁核等辅助模块，用于覆盖
CPU、I/O 和内存三类证据。

运行参数主要围绕 PSI 门控和日志输出控制展开。其中，resource
用于指定关注的压力资源类型，可以面向 CPU、I/O、内存或任意资源；window
用于指定 PSI 统计窗口；index 用于区分不同压力指标；threshold
用于设置进入压力窗口的触发阈值；interval
用于控制部分汇总输出的时间间隔；save
参数用于控制是否将事件写入设备侧日志文件。本文实验默认采用较保守的阈值设置，使系统在低压阶段保持较小输出，在压力升高时保留更密集的核心事件。这样的参数化设计也便于后续针对纯
I/O 场景或强内存场景调整门控策略，而不必修改主程序结构。

需要强调的是，用户态运行参数控制的是采集链路的启用组合、门控判断和日志保留策略，而不是在高压后才临时加载内核探针。eBPF
程序在启动阶段已经完成挂载，运行时 PSI
门控主要决定事件是否被提交、保留或写入日志。该实现边界与第三部分的系统设计保持一致：在线阶段尽可能减少无效日志和设备侧开销，异常阶段保留可解释证据；离线阶段再通过结构化解析和窗口构造完成统计分析。通过配置化用户态程序，本文能够在不同压力场景下复用同一原型，并保证实验结果与具体运行参数之间具有明确对应关系。

## C. 实验自动化

实验自动化模块用于降低人工操作对真机实验结果的影响。Android
设备上的压力状态、后台进程和交互路径具有较强波动性，如果每轮实验都依赖手动启动程序、记录时间和拉取日志，容易引入停止时刻不一致、日志遗漏、压力进程残留和元数据缺失等问题。为此，本文编写
PowerShell 和 Python
脚本对实验流程进行封装，使每轮运行都能够自动创建目录、保存配置、启动采集、施加压力、停止进程、拉取日志并进入离线解析流程。

单轮实验以 run 为基本单位。脚本首先创建独立 run
目录，并记录设备状态、实验场景、运行时长、压力类型、启动时间和配置文件等元数据；随后通过
ADB 在设备侧启动 PerfInsight 或对照工具，并根据实验类型启动
CPU、I/O、内存或混合压力负载；实验达到预设时长后，脚本按顺序停止监测程序和压力进程，拉取设备侧日志，并保存标准输出、错误输出和运行摘要。这样的流程使每个
run 都具有完整的输入配置和输出证据，便于后续复查某一轮结果的来源。

为避免观测工具之间相互影响，基础对照实验遵循"每轮只运行一种观测工具"的原则，即
PerfInsight、top 和 PSI
采样分别独立运行。这样可以减少不同工具同时运行带来的额外调度和 I/O
干扰，使日志规模、CPU
忙碌度和压力信号更接近对应工具自身的观测结果。对于需要进行时间对齐的同步实验，脚本则在同一
run 中同时保存 PerfInsight、PSI、top 和 gfxinfo
等字段，并通过统一时间戳构造一秒窗口。本文在结果分析中区分基础对照实验和同步采样实验，避免将两类数据混作同一种实验条件。

自动化脚本还承担异常清理和数据边界控制功能。每轮实验结束后，脚本会清理压力进程和后台采样进程，防止上一轮残留负载影响下一轮；离线解析阶段则根据正式
run 白名单读取数据，排除
dryrun、脚本调试和异常中断样本。该设计使实验数据不仅能够批量采集，也能够保持可复现和可审计。后续若扩展到更多设备或更多轮次实验，只需要调整场景配置和运行清单，而不需要改变核心采集程序和解析链路。

## D. 离线解析

离线解析模块负责把设备侧采集的原始日志转换为可统计的数据表。由于
PerfInsight 输出包含门控状态、runtime、I/O 延迟、调度事件、buddy
状态以及实验脚本保存的 top、PSI 和 gfxinfo
等辅助信息，原始日志本身并不适合直接写入论文结论。解析脚本首先读取每个正式
run
的日志目录和元数据文件，确认场景、运行时长、压力类型和采集配置，再分别处理不同模块的日志格式。这样可以避免把不同来源、不同粒度的数据混合统计。

在具体处理过程中，解析脚本采用流式读取方式提取关键字段，包括日志行数、事件数量、运行时延迟、I/O
排队与执行延迟、P95 指标、PSI 峰值、top
忙碌度以及用户侧帧耗时标签等。解析结果被组织为多类 CSV 文件，例如
run_summary 用于描述每轮实验的整体结果，module_log_summary
用于比较不同模块输出规模，psi_summary
用于记录压力信号变化，io_latency_summary 和 cpu_runtime_summary
用于统计延迟分布。通过这些中间表，论文中的均值、范围、P95
和图表均可以追溯到具体 run 和原始日志。

对于同步采样实验，离线解析进一步构造一秒时间窗口，将 PerfInsight
日志、PSI、top 和 gfxinfo
字段对齐到统一时间轴。窗口化处理的作用在于把不同采样频率、不同日志格式的数据转化为可比较的结构化指标，使系统侧压力证据能够与用户侧帧耗时标签建立关联。本文当前使用该窗口数据进行
Jank
关联分析和候选证据排序，但不将其解释为严格因果根因定位；这一边界由解析报告和第五部分实验分析共同保持。

离线解析还承担论文图表和机器学习数据集的输入准备工作。脚本在生成 CSV
后进一步汇总正式场景数据，绘制日志规模、延迟分布、top 忙碌度、gfxinfo
ground
truth、候选证据热力图和压力状态识别相关图表。与此同时，解析阶段只读取正式
run 白名单，并排除
dryrun、参数试探和异常中断样本，保证图表和模型输入与论文实验设计一致。由此，离线解析不是简单的日志格式转换，而是连接真机采集、统计分析和论文结论的关键步骤。

# V. 实验评估

## A. 实验设置

实验目标是回答四个问题：第一，PerfInsight 内部的 PSI

eBPF
程序保存核心事件；第二，压力升高后系统能否捕获调度、I/O、内存分配和运行时变化；第三，PerfInsight
与 top、/proc/pressure
等系统工具之间是否形成互补证据；第四，底层压力证据能否与用户侧帧耗时标签建立可解释联系。正式实验以
OnePlus Ace 3 真机为对象，覆盖空闲、CPU 压力、I/O 压力、CPU+I/O

I/O、CPU+I/O、内存与三资源联合压力在 batch50
下表现出不同触发形态。CPU+I/O 场景的平均日志规模约为 281.030 MB，CPU PSI
峰值均值约为 37.538；三资源联合场景的平均日志规模进一步达到 341.132
MB，CPU PSI 峰值均值约为 41.239，说明多资源竞争更容易触发高强度输出。纯
I/O 场景的 I/O PSI 峰值均值约为 0.690，而日志规模仅约为 0.291
MB，表明当前门控策略对 I/O
停顿更敏感于"是否形成明显任务停顿"，而不是简单根据 I/O
负载本身放大输出。

内存压力和三资源联合压力在 batch50 中同样呈现非线性关系。内存场景的 MEM
PSI 峰值均值约为 0.409，高于空闲、CPU、I/O 和 CPU+I/O
场景，但平均日志规模仅约为 0.921 MB；三资源联合场景的 MEM PSI
峰值均值约为 0.389，与内存场景接近，而 CPU PSI 与 I/O PSI
同时更高，平均日志规模也明显放大。这说明 CPU、I/O
和内存压力不是简单线性叠加，PSI
观测到的是任务停顿压力的综合结果，最终触发强度仍受到压力时序、资源竞争方式和系统即时状态的共同影响。

## C. 延迟与调度证据

从延迟与事件证据看，CPU 压力、CPU+I/O 混合压力和三资源联合压力在 batch50
中均表现出较稳定的运行时延迟抬升。CPU 场景的 runtime P95 均值约为 3.932
ms，CPU+I/O 场景约为 3.907 ms，三资源联合场景约为 3.913 ms，说明当 CPU
竞争或多资源竞争出现时，系统能够在运行时延迟和事件强度上保留较一致的证据。

I/O 场景的解释仍需谨慎。尽管 batch50 中 I/O PSI 峰值均值约为 0.690，top
iowait 均值约为 1.258，但运行时延迟、I/O P95 和事件输出整体仍明显低于
CPU+I/O 和三资源联合压力。这说明当前门控策略能够感知 I/O 停顿，但纯 I/O
场景未必稳定进入高强度采集模式；更合适的解释是，I/O
压力只有在明显影响任务推进时，才会转化为更密集的 PerfInsight 证据。

新增内存压力样本对这一结论形成补充。单独内存压力下 I/O 延迟样本达到
75454 条，I/O P95 为 1.098 ms，runtime P95 为 0.608 ms，buddy 事件达到
671105 条，说明该场景的主要异常证据并非长
runtime，而是内存分配活动放大并伴随 I/O 与调度证据。三资源联合压力下 I/O
P95 为 1.964 ms，runtime P95 达到 3.962 ms，buddy 事件为 576269
条，说明联合压力更接近 CPU 调度与内存分配共同作用的状态。

## D. 跨工具对照

top 与 PSI 输出提供了系统级背景。top 显示 CPU 压力和混合压力下平均忙碌
CPU 分别约为 791.67% 和 782.93%（以 8 核总计 800%
为基准），而空闲状态仅约为 28.93%。PSI 对照采样中，CPU pressure 与 mixed
pressure 的 CPU some avg10 峰值分别达到 49.78 和 57.02，能够解释
PerfInsight 为什么在这些阶段触发更多核心采集。

与 top 和 PSI 相比，PerfInsight
的价值并不在于重复显示"系统繁忙"，而在于进一步给出繁忙背后的事件结构。例如
CPU 压力下可以观察 runtime 与 preemptive 行数的同步抬升；CPU+I/O
和三资源联合场景中可以观察块 I/O 延迟、buddy 行数与 preemptive
行数的联合放大；内存压力下则能够观察 MEM PSI 与 buddy
行数的同步变化。这种证据组合为后续定位"卡顿更接近调度竞争、I/O
路径还是内存分配路径"提供了基础。

![图4 top 对照工具记录的平均 CPU 忙碌度](media/image4.png){width="5.8in"
height="2.78082239720035in"}

为了避免只依赖自研原型解释实验现象，本文使用 top 对宏观 CPU

和内存场景的 busy 均值明显更低。top 能够回答"CPU
是否繁忙"，但无法解释繁忙来自 preemptive
事件、运行时延迟、伙伴系统活动还是块 I/O 阻塞。因此，top
用于确认宏观负载背景，PSI 用于确认任务停顿压力，PerfInsight
则进一步保留底层事件证据。三者形成互补后，本文方法相较传统工具的增量价值也更加明确。

## E. 用户侧 Jank 参照

为避免仅凭底层压力指标推断用户体验，本文补充 dumpsys gfxinfo
作为用户侧卡顿标签。轻量设置页滚动实验中，即使 CPU 压力和混合压力使 CPU

## F. 候选证据与 Jank 关联分析

在不引入端到端卡顿预测模型的前提下，本文首先采用"实验窗口特征---异常偏离度---多源证据排序---机制解释"的规则化证据排序。具体做法是以空闲场景作为基线，对
CPU scheduling、I/O path、Memory/allocation 和 Overall trigger intensity
四类候选机制构造窗口特征，并根据 PSI、runtime、队列长度、抢占、迁核、I/O
延迟、I/O 样本和 buddy
活动相对基线的偏离程度计算分数。该方法不声称证明因果关系，而是用于在现有样本量下给出可解释的候选证据排序。

重新整合新增数据后，结果定位更加清晰：CPU 压力和 CPU+I/O
压力的首要候选证据仍为 CPU 调度，主要依据来自 CPU PSI、runtime
P95、抢占与相关事件强度的同步升高；内存压力的首要证据转向内存/分配路径，体现为
MEM PSI 和 buddy
行数相对空闲场景的抬升；三资源联合压力的前两类候选集中在 CPU
调度与内存/分配，说明该场景不是单一 I/O
或单一内存现象，而更像调度竞争与分配活动共同作用。I/O
压力场景则仍表现为状态依赖：在 batch50 正式样本中，I/O PSI 和 top iowait
能稳定给出存储等待背景，但 PerfInsight 输出强度明显低于 CPU+I/O
和三资源联合场景，因此论文中将其作为可捕获现象和后续门控优化方向，而不写成稳定根因结论。

## G. 基于机器学习的压力状态识别与证据排序

在规则化候选证据排序之外，本文进一步利用 batch50_20260520
的六类正式场景构建轻量机器学习分析，用于验证 PerfInsight
多源指标是否能够稳定区分不同压力状态。这里的监督标签仍然是实验压力场景，而不是逐秒
gfxinfo 或 Perfetto
的用户感知卡顿标签，因此该分析的目标不是直接预测卡顿，而是检验系统级证据在压力窗口识别上的可分性，并为后续同步采样提供方法基础。

1）数据集构建与标签定义。机器学习数据集由逐秒同步采样结果聚合得到。本文选取空闲、CPU
压力、I/O 压力、内存压力、CPU+I/O 混合压力和
CPU+I/O+内存联合压力六类正式场景，每类 50 个 run，共 300 个 run
级样本。设第 r 个 run 的特征向量为 X_r，标签为 y_r，则分类目标可表示为：

*f(X_r) -\> y_r, y_r in {idle, cpu, io, mem, mixed, all}.*

其中，y_r 表示实验压力场景标签，而不是用户感知卡顿标签。之所以采用 run
级样本而不是直接把所有 1
秒窗口随机打散，是因为同一次实验内部的连续窗口具有明显时序相关性；若将同一
run
的窗口同时放入训练集和测试集，模型可能记住某轮实验的局部波动，从而高估泛化能力。因此，本文以
run_id 作为分组单位进行训练测试划分和交叉验证。

2）特征构造。特征处理遵循"窗口统计---滞后统计---run
级补充"的思路。首先，对同步窗口中的 PSI、top 和 PerfInsight
秒级指标计算均值、最大值、标准差和 P95
等统计量，用于描述单轮实验内压力强度和波动范围。对任一指标 x，其在 run r
内的窗口统计特征可表示为：

*phi_r(x) = {mean(x), max(x), std(x), P95(x)}.*

其次，构造 t-1s、t-3s、t-5s 和 t-10s
等滞后特征，用于观察资源压力在状态变化前后的先导性：

*x_t\^(Delta) = x\_(t-Delta), Delta in {1s, 3s, 5s, 10s}.*

最后，本文加入 PerfInsight 的 run 级统计，包括日志规模、runtime
事件数量和 P95、I/O 事件数量和 P95、buddy 行数以及 preemptive
行数等。不同特征集合被划分为 base_window_stats、base_plus_run_stats 和
base_run_lag_stats 三类，以比较基础窗口统计、run
级补充和滞后特征对识别效果的影响。

3）模型与评价方法。本文没有引入复杂深度学习模型，而是采用
LogisticRegression、RandomForest 和 GradientBoosting
三种常见方法进行对照。LogisticRegression
作为线性可解释基线，用于检验压力状态是否能被简单线性边界区分；RandomForest
能够刻画非线性特征组合，并提供特征重要性，因此作为本文证据排序的主要模型；GradientBoosting
作为另一类集成树模型，用于检查增强式非线性模型是否能带来额外收益。评价方式包括以
run_id 为分组的 GroupKFold 交叉验证和按 run 划分的 holdout
测试，其中训练集为 210 个 run，测试集为 90 个
run。候选证据按照模型特征重要性排序，可表示为：

*Rank = argsort_k(Imp(k)),*

其中 Imp(k) 表示第 k
个特征在模型中的重要性分数。这样的设置保证测试样本来自未参与训练的完整实验轮次，也使特征重要性能够作为候选证据排序，而不是被解释为严格因果依据。

从整体分布看，PCA 前两主成分已经解释了大约 69.8% 的样本方差，其中 PC1
约为 46.8%，PC2 约为
23.0%。这说明样本在低维空间中具有较强的可分性。图10展示了六类压力样本在
PCA
空间中的投影，可以看到空闲样本与高压样本整体上分布在不同区域，CPU、I/O、内存和混合压力则在不同方向上形成各自的聚集趋势，说明
PSI 与 PerfInsight
的联合特征并非纯噪声，而是确实携带了可辨识的压力状态信息。

![图10 六类压力场景的 PCA 分布](media/image10.png){width="5.8in"

图10的意义不在于证明某个场景可以完全线性分开，而在于说明系统观测信号具有稳定的结构性差异。尤其是空闲样本与强压力样本的距离较大，表明

筛选和底层事件采集保留了足以区分运行状态的证据；而混合压力和三资源联合压力出现一定重叠，则进一步说明多资源竞争本身具有交叉影响，这与前文对门控敏感性和联合压力非线性的讨论是一致的。

事件数量、buddy 活动、preemptive
行数和日志规模的共同升高，表明多资源竞争不是单一指标的线性放大，而是在多个子系统中同时留下证据。对于单独内存压力，batch50
数据中的触发强度弱于早期强内存单轮实验，但模型仍能通过低 CPU/I/O
活跃度、内存相关 PSI 变化和少量 buddy
统计将其与其他场景区分开来，这也提示本文的门控结果应解释为"实际资源停顿状态"的反映，而不是简单的压力工具标签。

MEM PSI 较低而 CPU 与 I/O 证据占主导时，它与 CPU+I/O mixed
场景会更加接近。LogisticRegression 作为线性基线同样达到 0.989 的 holdout
准确率，说明压力状态在特征空间中已经具有较强可分性；GradientBoosting
的结果略低，用于作为非线性增强模型对照。因此，本文将机器学习结果解释为压力状态可分性和候选证据排序，而不是对每一类压力源作绝对独立的因果判定。

从论文表达上看，这里更适合写成"证据排序"而不是"黑箱预测"。因为特征重要性告诉我们的不是因果终点，而是不同压力状态下哪些系统证据更稳定、更有区分力。对于当前数据集，这已经足以支撑论文中的方法有效性论证：PerfInsight
采集到的并不是孤立日志，而是一组在统计上可用于区分压力状态的结构化证据。

## H. 讨论

综合来看，实验结论可分为五层。第一，PSI
作为资源停顿压力指标和潜在卡顿窗口筛选信号，能够在空闲场景中显著抑制无效日志，并在
CPU、CPU+I/O 等重复压力场景中稳定触发核心采集。第二，eBPF 事件能够补足
top 和 PSI 无法提供的细粒度证据，使调度竞争、强 I/O
状态和运行时延迟可以被结构化保存。第三，内存压力与三资源联合压力目前作为补充覆盖场景，用于说明
PerfInsight
能够观测内存分配路径和多资源竞争边界；由于这两类场景当前各为一轮样本，本文不将其写作稳定重复统计规律。第四，用户侧
gfxinfo 结果表明，轻量交互在压力下不一定卡顿，而重应用启动和多 App
切换更容易形成明显 Jank；重交互同步实验进一步将 3626
帧用户侧数据与系统指标对齐，证明本文链路可以进入窗口级证据分析。第五，机器学习和规则化分类结果共同说明，PerfInsight
采集到的是具有统计可分性和解释价值的结构化证据，但当前结论仍应表述为压力状态识别、Jank
关联分析和候选机制排序。

当前实验仍存在局限：第一，正式数据集仍只有一台 OnePlus Ace 3
真机，跨设备泛化仍需后续补充；第二，逐秒 gfxinfo 同步已经打通并扩展到 6
轮重交互样本，但样本规模仍不足以支撑泛化的用户卡顿预测模型；第三，Perfetto
pilot 目前因设备侧 trace
输出权限问题尚未纳入同一解析链路，后续需要修正采集路径或权限后再作为更细粒度
trace ground
truth；第四，内存压力和三资源联合压力目前仍需要更多重复实验验证；第五，强触发状态下日志量仍较大，后续应继续优化采样策略、缓冲策略和分资源门控阈值。

# VI. 相关工作

Android
性能分析与卡顿诊断已有较为丰富的工具链。Perfetto、systrace、simpleperf、logcat
和 dumpsys 等工具能够从不同角度提供系统运行信息：Perfetto 和 systrace
适合记录较完整的系统 trace，simpleperf 更侧重采样式性能分析，logcat
能反映应用和系统日志，dumpsys gfxinfo 则可以提供帧耗时和 Jank
相关统计^\[3\]\[5\]\[6\]^。这些工具在问题复现、离线调试和开发者分析中具有重要作用，但通常需要明确的采集窗口、人工触发或较强的离线解释能力。对于偶发性卡顿或运行时资源压力变化，仅依赖事后
trace 往往难以保证异常发生前后的底层上下文被完整保留下来。

与传统调试工具相比，本文关注的是面向真机运行的异常监测链路，而不是替代
Perfetto 或 simpleperf。Perfetto 可以提供更完整的时间线和 FrameTimeline
信息，适合作为用户侧 ground truth 或深度 trace
分析工具；top、/proc/pressure 和 dumpsys
等接口能够提供宏观状态或帧级表现；但它们通常不能直接给出调度、I/O
和内存路径中的细粒度事件结构。本文的设计思路是利用这些工具作为对照和标签来源，同时通过
PerfInsight
在压力窗口中保留内核侧候选证据，从而把"是否出现卡顿或压力"进一步连接到"压力窗口内哪些系统路径更活跃"。

持续追踪和生产环境调试方面，Hubble 等研究说明了在真实 Android
环境中保留运行时上下文对于性能问题定位的重要性^\[16\]^。这类工作通常强调在应用运行过程中捕获有价值的调用或执行上下文，以便在问题发生后进行定位分析。相关研究表明，移动系统中的响应性问题并不总是来自单一负载升高，而可能涉及进程管理、后台任务、交互路径和系统资源竞争等多方面因素^\[1\]\[2\]^。本文与这类工作的共同点在于关注真实设备上的运行时证据保留；区别在于本文不依赖应用运行时代码插桩或更深层系统栈改造，而是从
eBPF 和 PSI 出发，构建面向内核事件和资源停顿压力的轻量观测原型。

eBPF
相关研究和工具已经证明其在系统观测、安全检测和性能分析中的低侵入优势^\[7\]\[17\]\[8\]\[18\]^。在服务器和云环境中，eBPF
常用于追踪系统调用、网络路径、调度行为和安全事件；在 Android
场景中，AOSP 也提供了 eBPF loader
和相关基础设施，用于系统统计、网络和平台级监控^\[9\]^。同时，面向嵌入式
Linux
的可观测性研究也强调，资源受限设备中的事件过滤、低开销采集和离线分析同样重要^\[19\]^。随着
GKI、BTF 和 libbpf CO-RE 机制的发展，eBPF 在 Android
真机上的适配条件逐步改善^\[10\]^。然而，移动设备相比服务器具有更强的功耗、温控、权限和前后台调度约束，若直接将服务器侧持续采集思路移植到
Android，容易带来日志量过大和运行开销问题。因此，面向 Android
卡顿和异常监测的 eBPF 方案需要结合移动端特征进行事件选择和采集控制。

PSI 相关工作则从资源停顿角度补充了传统利用率指标的不足。PSI 描述任务因
CPU、内存或 I/O
资源竞争而无法继续推进的时间比例，能够反映任务受到资源压力影响的程度^\[11\]\[12\]^。相比
CPU 使用率、剩余内存或 I/O 吞吐这类宏观指标，PSI
更接近本文关注的"任务推进是否受阻"这一问题。因此，本文没有把 PSI
仅作为外部对照指标，而是在 PerfInsight
中将其实现为压力窗口筛选和采集门控依据。需要强调的是，PSI
并不等同于用户感知卡顿标签，本文将其定位为异常窗口的系统侧先验信号，再结合
eBPF 事件和 gfxinfo 标签进行关联分析。

综上，现有工作大致可以分为三类：第一类是 Android 平台工具和 trace
系统，优势在于信息完整和生态成熟，但更偏向复现式调试和离线解释；第二类是生产环境持续追踪研究，强调真实运行上下文保留，但往往需要运行时或系统栈层面的特定改造；第三类是
eBPF 和 PSI 相关系统观测机制，能够提供低侵入内核观测和压力停顿信号，但在
Android
卡顿监测场景中仍需要解决日志量控制、多源证据组织和用户侧标签关联等问题。本文的差异在于将
PSI 门控模块、eBPF
多源事件采集、自动化真机实验和离线窗口化分析连接为一条完整链路，并将结论限定为异常监测、压力状态识别、Jank
关联分析和候选证据排序，而不将当前结果夸大为端到端自动根因诊断。

# VII. 总结

本文围绕 Android 系统卡顿和资源异常监测问题，提出并实现了一种结合 eBPF
与 PSI 的多源观测方法。该方法以自研原型 PerfInsight 为载体，在用户态集成
PSI 监测与门控模块，并加载 eBPF 程序挂载到 CPU 调度、块
I/O、内存分配和运行时等关键内核路径。系统启动阶段完成 eBPF
加载、挂载和缓冲区初始化，运行阶段利用 PSI
筛选资源停顿压力窗口，并在压力窗口内保留更细粒度的内核事件证据。离线阶段进一步将原始日志、run
元数据和同步采样结果整理为结构化 CSV、统计图表和候选证据排序结果。

基于 OnePlus Ace 3 真机的多场景实验表明，PerfInsight
在空闲状态下能够保持较小输出，并在 CPU、CPU+I/O
等重复压力场景下捕获较稳定的调度、延迟和资源压力证据。纯 I/O
场景表现出与设备即时状态和门控阈值相关的状态依赖；内存压力和三资源联合压力则作为补充覆盖场景，说明原型能够观测内存分配路径和多资源竞争边界，但不被解释为稳定重复统计结论。重交互同步实验进一步将系统侧指标与
gfxinfo 帧耗时结果对齐，形成 Jank
窗口关联分析基础；机器学习压力状态识别结果也表明，PerfInsight、PSI 和
top 等多源指标具有较强的统计可分性，可以用于压力状态识别和候选证据排序。

需要强调的是，本文的结论限定在异常监测、压力窗口筛选、Jank
关联分析和候选证据排序层面。PSI
在本文中不是用户感知卡顿的唯一标签，机器学习模型的监督标签也是实验压力场景而不是逐帧卡顿标签；特征重要性和滞后相关结果用于说明哪些系统证据更有区分力，而不被解释为严格因果根因定位。这样的边界使本文结论与现有数据规模和实验条件保持一致，同时也为后续扩展到更严格的卡顿标签建模和因果验证保留空间。

未来工作将从三个方向展开：第一，在现有 PerfInsight、PSI、top 与 gfxinfo
的逐秒同步链路上继续扩大重交互样本规模，并修复 Perfetto trace
输出权限与解析流程，使用户侧标签更加完整；第二，在更多 Android
设备和不同内核版本上验证 BTF、Root、eBPF 加载和 PSI
门控策略的适配性，并补充内存及联合压力的重复实验；第三，继续优化采样开销、日志写入策略和分资源门控阈值，在结构化数据基础上探索更稳健的自动化候选证据分析方法。
