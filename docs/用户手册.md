## 2. 项目简介

EulerPilot 是面向 openEuler 的自适应资源管控 Agent。它不是单一调度器 demo，而是一套围绕以下闭环构建的系统级 Agent 框架：

```text
观测 -> 分类 -> 策略决策 -> Skill 执行 -> 审计 -> 回滚 -> 证据
```

核心能力包括：

- 用 eBPF、PSI、LSM、TC/XDP、sched_ext map 等收集 workload 和系统压力信号。
- 在用户态 Agent 中完成 workload 分类、策略门控、target 解析和跨 Skill 编排。
- 通过 cgroup v2、sched_ext/scx、TC、XDP、BPF LSM 等系统控制器执行资源治理或策略验证。
- 通过 AuditBus、ActionJournal、JSONL 事件、report、manifest 和 Web Console 形成可审计证据链。
- 在 Agent stop、失败注入或 cleanup 阶段执行 rollback，并尽量保证只清理 EulerPilot 自有 lab 资源。

项目价值不是宣称所有 workload 永远提升，而是证明系统能观测、决策、执行、回滚，并把收益、代价和边界讲清楚。

## 4. 功能总览

已注册 Skill 可通过命令查看：

```bash
./build/eulerpilot-agent --list-skills
```

当前主线输出应包含：

```text
network_policy
network_policy_demo
network_qos
network_xdp
policy_engine
psi_gate
resource_control
security_policy
security_policy_demo
```

功能分层如下：

| 层级 | 模块 | 说明 |
|---|---|---|
| 观测层 | `bpf/`、PSI、LSM、TC/XDP、sched_ext stats | 采集 workload、压力、安全事件和调度统计。 |
| 控制层 | `agent/` | Runtime、配置解析、Analyzer、TargetResolver、SkillManager、PolicyEngine。 |
| 执行层 | cgroup v2、scx、TC/XDP、BPF LSM | 执行资源控制、网络策略、安全策略和调度实验。 |
| 证据层 | `reports/`、`results/`、`evidence/`、`dashboard/` | 保存测试结果、事件、图表、manifest 和最终报告。 |
| 展示层 | `web_console/`、`docs/`、`demo/` | Agent 状态展示、白名单演示、答辩材料和用户手册。 |

建议先执行只读环境检查：

```bash

```

![image-20260727091101021](assets/user-manual/image-20260727091101021.png)

常见依赖包括：

- `clang`、`llvm`、`bpftool`、`libbpf` 相关开发包。
- `make`、`gcc/g++`。
- `tc` / `iproute2`。
- Node.js 与 npm，用于 Web Console。
- Redis/Nginx/wrk/stress-ng 等 benchmark 依赖，只有跑实验时需要。
- Kubernetes/k3s/kubectl，仅真实 Pod 验证需要。

只读命令通常不需要修改系统状态，但 BPF、cgroup、TC/XDP、LSM、sched_ext 和 Kubernetes live/lab 验证需要 root。建议使用专用验证机，不要在生产环境直接执行。

### 6.3 cgroup v2 初始化

在验证机上初始化 EulerPilot lab cgroup：

```bash
sudo scripts/setup_cgroup_v2.sh
```

![image-20260727091123810](assets/user-manual/image-20260727091123810.png)

当前 release 默认安全关闭 cpuset，稳定路径使用 `cpu.weight/cpu.max`、memory 和 IO 控制器。只有显式实验才启用 cpuset。

## 10. Agent 运行模式

| 模式 | 命令或配置 | 含义 |
|---|---|---|
| dry-run | `agent.mode: dry-run` 或不加 `--active` | 只观测、分类和输出，不写系统控制器。 |
| active | 加 `--active` | 允许启用配置中声明的 enforce/控制动作。 |
| cgroup_v2 backend | `--backend cgroup_v2` | 官方发行内核稳定执行后端。 |
| sched_ext backend | `--backend sched_ext` | 需要自编译启用 sched_ext 的内核和 formal scx artifact。 |
| always-active gate | `--gate-mode always-active` | 不依赖 PSI，适合短时集成测试。 |
| psi gate | `--gate-mode psi` | 依据 PSI 状态机进入 ACTIVE/COOLDOWN。 |
| normal gate | `--gate-mode normal` | 保守模式，通常用于只读或低风险启动。 |

演示 dry-run 输出示例中，`mark` 列含义：

```text
. observe   + apply   ~ manage   - none
L latency   B background   T batch
```

如果看到 `L redis-server ... |~ normal_profile ... no-group-for-class`，说明 Agent 已识别 Redis 为 latency-sensitive，但当前没有对应可管理 cgroup 或处于 dry-run/非写入状态。

## 11. 输出界面与状态解释

### 11.1 CLI 表格输出

典型输出结构：

```text
EulerPilot Agent
config: configs/agent.yaml
interval: 1000ms  duration: 10s
mode: dry-run  backend: cgroup_v2
env: psi:ok  cg:ok  scx:--

mark name pid class act profile w:weight reason
```

字段说明：

| 字段 | 说明 |
|---|---|
| `name` | 进程 comm，可能被内核截断。 |
| `pid` | 进程 ID。 |
| `class` | Analyzer 分类结果，如 latency、batch、background 或 unknown。 |
| `act` | 当前动作，`apply/manage/none` 等。 |
| `profile` | 匹配到的资源 profile。 |
| `reason` | 为什么应用或不应用动作，例如 `non-target-process`、`target-scope-mismatch`。 |

### 11.2 status JSON

```bash
./build/eulerpilot-agent --status --json
```

![image-20260727093507683](assets/user-manual/image-20260727093507683.png)

当前输出包含：

- `cpuset_control=disabled`：封版安全策略，当前稳定路径使用 `cpu.weight/cpu.max`。
- `skills[]`：每个 Skill 的 available、running、state、evidence。
- safe status 下 `available=false/running=false/state=created` 不代表功能不可用，而是未启动 live probe；需结合 `reason=ok` 和 doctor/capability 判断。

### 11.3 doctor-safe

```bash
./build/eulerpilot-agent --doctor-safe --config configs/agent.yaml
```

![image-20260727093538594](assets/user-manual/image-20260727093538594.png)

`doctor-safe` 严格只读，不加载 BPF/TC/XDP/LSM，不创建 cgroup。Skill 行显示 `safe-not-probed` 是预期行为。

## 12. Workload Observer 与 Analyzer

Observer 负责采集 workload 行为指标，Analyzer 负责把样本分类为 latency-sensitive、throughput/batch、background/noisy 或 unknown。

常见输入信号包括：

- 进程 comm、PID/TID/TGID。
- wait/runtime/wakeup/migration/context switch 类指标。
- PSI pressure。
- sched_ext stats 或 cgroup stats。

封版实现要求使用任务身份和 delta 语义避免 PID/TID 重用、counter reset、无符号下溢和跨任务串样本。用户侧不需要直接操作这些内部结构，但应理解：性能和分类结论必须来自同一 tested commit 和 formal artifact，不能混用旧二进制或旧 trace。

## 13. PSI Gate 与自适应策略

PSI Gate 用于把系统压力从“持续写控制器”改为“压力窗口内激活”。状态机口径：

```text
NORMAL -> ARMED -> ACTIVE -> COOLDOWN -> NORMAL
```

使用方式：

```bash
sudo ./build/eulerpilot-agent --backend cgroup_v2 --gate-mode psi --active --duration-s 60
```

![image-20260727093719429](assets/user-manual/image-20260727093719429.png)

Mixed-Adaptive 验证要求同一个 Agent 实例连续经历 quiet、pressure、recovery，不允许把多个 Agent 的 trace 拼接成闭环。该能力定位为功能闭环验证，不作为净性能提升结论。

## 14. Resource Control Skill

Resource Control 是 EulerPilot 的 cgroup v2 主执行 Skill。

### 14.1 能力

- CPU：`cpu.weight`、`cpu.max`。
- Memory：`memory.high`、`memory.low`、`memory.max`。
- IO：`io.weight`、`io.max`。
- target：cgroup、PID、container、container_id、Kubernetes Pod。
- rollback：读取旧值、写入新值、复读验证、失败恢复。

当前 release 默认 `cpuset_control=disabled`，不宣传动态 cpuset 拓扑管控已作为完整能力启用。

### 14.2 快速检查

```bash
./build/eulerpilot-agent --status --json | jq '.cpuset_control, .skills[] | select(.name=="resource_control")'
```

## 15. Network Policy Skill

Network Policy 覆盖三类网络能力：

- `cgroup_connect4`：按 cgroup scope 观测或拒绝 connect。
- `network_qos` / TC：在 lab veth 或解析出的 Pod host veth 上做 QoS 限速。
- `network_xdp`：在 isolated veth 或 lab Pod veth 上做 XDP drop/pass 验证。

安全边界：

- 默认只允许 lab 接口：`veth*`、`ep-*`、`lab-*` 或配置显式声明接口。
- 默认拒绝管理网卡、默认路由接口和当前 SSH 路径接口。
- audit 模式必须只读，不应创建或删除 cgroup。
- 外部业务 cgroup 封版默认严格只读。

常用测试：

```bash
sudo tests/integration/test_network_policy.sh
sudo tests/integration/test_network_qos_tc.sh
sudo tests/integration/test_network_xdp.sh
```

清理：

```
sudo scripts/cleanup_network_policy_demo.sh || true
sudo scripts/cleanup_network_qos_tc.sh || true
sudo scripts/cleanup_network_xdp_demo.sh || true
```

## 16. Security Policy Skill

Security Policy 使用 BPF LSM 和 syscall tracepoint 形成安全策略和 anomaly 证据。

### 16.1 能力

- file open / bprm exec / socket connect / ptrace / capability / credential lifecycle 等 LSM hook。
- `execve`、`openat`、`connect`、`ptrace` tracepoint 观测。
- `burst_execve`、`burst_connect`、`burst_openat_sensitive`、`capability_abuse`、`credential_churn` anomaly。
- scoped enforce：file/exec/socket enforce 必须有 target/cgroup scope。

### 16.2 安全口径

如果目标内核不能可靠读取 socket 协议，socket enforce 应 fail-closed 标为 unavailable；不能把“只按端口匹配”描述为 TCP enforce。无 scope 的全局 enforce 在封版配置中应拒绝启动。

### 16.3 测试

```bash
sudo tests/integration/test_security_policy.sh
sudo tests/integration/test_security_policy_anomaly_rules.sh
sudo tests/integration/test_security_policy_credential_anomaly.sh
```

清理：

```
sudo scripts/cleanup_security_policy_demo.sh || true
```

## 17. Policy Engine 跨 Skill 联动

Policy Engine 消费 Security anomaly 或其他 Skill 事件，并触发 Resource/Network 等白名单动作。

核心链路：

```text
security_policy burst_connect anomaly
  -> policy_engine decision
  -> resource_control demo_cgroup cpu.max / memory.high
  -> network_qos lab_netdev tc/tbf 2mbit
  -> AuditBus + ActionJournal
  -> Agent stop rollback
```

配置入口：

```bash
./build/eulerpilot-agent --validate-config configs/policy_engine_security_network_resource.yaml
```

主演示测试：

```bash
sudo tests/integration/test_policy_engine_security_network_resource.sh
```

连续验证：

```bash
sudo tests/integration/test_policy_engine_security_network_resource.sh --repeat 10
```

![image-20260727100508393](assets/user-manual/image-20260727100508393.png)

验收时应能用同一个 `transaction_id` 串起：security anomaly、policy decision、resource applied/restored、network applied/restored 和 ActionJournal。

## 18. sched_ext/scx 后端

## 28. 故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `--status` 中 Skill `available=false` | safe status 未执行 live probe | 结合 `reason=ok`、doctor-safe 和具体测试判断；这不等于功能缺失。 |
| Web 按钮被拒绝 `mutation_token_required` | 未设置 `EULERPILOT_CONSOLE_TOKEN` | 设置 token 后重启 Web Console，并在 URL 中带 `?token=...`。 |
| SSH 隧道报 administratively prohibited | SSH 服务端禁用端口转发 | 使用允许转发的跳板机或调整 SSH 服务端策略；不要直接暴露 root 控制台。 |
| SCX 无法启动 | 内核未启用 sched_ext 或 artifact 不匹配 | 先使用 cgroup_v2 后端；SCX 只在 SP4 自编译内核和 formal artifact 下验证。 |
| `doctor-safe` 显示 `safe-not-probed` | 预期行为 | safe doctor 不加载探针，需 live/integration 才能验证实际 attach。 |
| benchmark 数字与报告不同 | 可能是旧 evidence/provisional 或不同 tested commit | 查看 `evidence_status_overrides.json`、run manifest、tested commit 和 artifact id。 |

## 29. 性能结论阅读边界

当前正式口径：

- cgroup v2 是官方发行内核上的稳定执行后端。
- Redis GET/INCR 和部分 Nginx 场景在修正 baseline 后可呈现正向收益，但应按具体 workload、RUNS 和 CI 解释。
- SCX 控制链、DSQ 记账和 mixed-adaptive 状态闭环可运行；性能可能 improved、neutral 或 regressed，不能笼统宣传稳定全面提升。
- Mixed-Adaptive 是功能闭环验证，不是净性能实验。
- Agent overhead 应以 CPU 占用、RSS 和运行模式说明。

阅读报告时优先看：effect summary、paired 95% CI、每轮原始点、validity、performance_result、artifact provenance、cleanup result。

## 30. 交付、bundle 与 release 注意事项

封版前应区分：

| 名称 | 含义 |
|---|---|
| `tested_candidate_commit` | 候选源码 SHA，必须通过 candidate-bound gates。 |
| `tested_code_commit` | 全部门禁对同一 SHA 通过后确认的正式被测源码。 |
| `artifact_id` | 由源码、构建脚本、编译器、依赖、BTF、环境白名单等计算出的不可变构建产物身份。 |
| `release_candidate_commit` | 实验后加入报告、图表、evidence、release 元数据的候选提交。 |
| `release_commit` | 最终 release gate 通过后确认的提交。 |

正式 release bundle 应在仓库外生成，避免 manifest 自引用导致 commit SHA 失效。未经明确要求，不 push 分支、不 push tag、不创建远端 Release。
