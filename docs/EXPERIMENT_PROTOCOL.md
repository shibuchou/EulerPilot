# 性能与可靠性实验协议

版本 v0.2，2026-10-21。以下是待执行协议，未生成 v2 性能数据。正式运行前在 pilot 后填好机器、阈值、种子和构建指纹并冻结。

## 1. 要回答的问题

H1：同样硬件/资源预算下，v2 相对默认 fair 能否改善业务性能？H2：相对同样优先级资源治理的强基线，调度数据面是否有额外收益？H3：相对固定最佳专家，Agent在相位变化/未见负载上是否更稳？H4：这些收益是否满足quiet开销、后台进度和恢复约束？

不以仅提高前台QPS作为系统总体优化的充分证据。将“业务保护”与“总吞吐提升”分开陈述。

## 2. 主环境与公平条件

主环境为 openEuler 24.03-LTS-SP3，所有主实验臂在同一内核启动、同一应用版本和同一 cgroup/CPU 配置下运行。默认fair基线是在该支持scx的内核上卸载scx，避免混入内核差异。发行默认内核可另列环境对照，不混入同一配对表。

每次记录：CPU/NUMA/SMT/LLC、宿主与VM版本/超售、steal、频率/温度、governor/turbo可控性、内存/交换、IRQ/软中断、后台服务、内核cmdline/config/BTF、PMU有效性、应用数据集与网络拓扑。无法控制的项目保留实际值，不伪称“固定”。

服务和干扰共享预先指定CPU池；客户端使用独立物理核/CPU池或独立机器，检查客户端无瓶颈。公平性实验不允许只有优化臂缩小BG CPU池/改quota/改nice；这种复合治理需独立标为另一实验组，并有同预算fair+cgroup对照。

所有臂的任务角色来自同一份授权目标列表。若使用手工BG标签，标记 `role_source=explicit`；未知角色另做自动行为分类实验，不能声称盲测识别了业务优先级。

## 3. 实验臂

| ID | 模式 | 目的 |
|---|---|---|
| A0 | 默认fair，仅必要业务测量 | 主要用户收益基线 |
| A1 | 默认fair + 同等观测 + Agent shadow | 隔离监控/控制面成本 |
| A2 | 默认fair + 静态cgroup优先级/预算 | 检查普通资源倾斜能解释多少收益 |
| B | BASIC scx + 同等观测 | 数据面基础成本，不默认低开销 |
| C | CLASS scx + 固定专家/行为分类 | 静态数据面能力 |
| D | ADAPTIVE scx + 规则路由/门控 | 新Agent完整主臂 |
| E | SchedPilot参考daemon | 新旧控制面一致性，对照互斥运行 |
| X | 一个能在同ABI上稳定运行的上游scx | 外部强对照，固定源码/配置；不刻意挑失败示例 |

P0短跑A0/B/C；正式主线A0/A1/A2/C/D，B按开销问题保留。各固定专家都在pilot选定后冻结，不能用测试集每轮oracle最佳专家作可部署基线。可另报告离线oracle上界并明确不能部署。

消融在主线成立后进行：`D-no-router`（同预算固定专家）、`D-no-gate`、`D-no-preempt`、`D-no-llc`、`D-no-pmu`、`D-no-bg-priority`。每个消融只改声明的一项，保留参数和作用域差异。PMU/LLC无效的机器不报告相应优化贡献。

## 4. 场景与负载

| 场景 | 内容 | 关键判据 |
|---|---|---|
| quiet | 无人工干扰 | 吞吐回归、尾延迟、Agent/执行服务成本 |
| noisy-cpu | CPU干扰，服务与BG共享池 | 前台goodput及BG完成率/最长等待 |
| noisy-mixed | CPU+内存，必要时另加I/O | 区分CPU与内存瓶颈，记录PSI |
| phase-change | quiet→noisy→mix→quiet | 识别/切换/恢复时延、抖动、总损失面积 |
| mixed-foreground | 两个前台服务竞争 | 联合SLO、资源隔离、冲突参数处理 |
| unknown/unsupported | PMU无效、低置信度、新任务 | 保守退化与可解释状态 |

Redis GET/INCR/SET分开报告，不只选最好命令；固定连接数、pipeline、keyspace、数据大小、读写比、持久化配置与服务线程。Nginx固定worker、keepalive、响应大小、TLS状态和请求生成器配置。MySQL只有在数据集、缓存状态和基线方差可控制后加入，不用小样本追逐优势。

closed-loop吞吐测试与固定到达率/SLO测试分开。closed-loop客户端会因服务变慢而降低发压，产生协调遗漏风险；报告到达率、实际完成率、排队/超时和客户端瓶颈。不要从分位数表推算goodput。

## 5. 指标定义与底线

- throughput：成功完成请求/秒；QPS、RPS、TPS保留业务定义。
- goodput@SLO：窗口内成功且请求延迟不超SLO的请求数/秒；需逐请求或足够精确的直方图计数，不能用“p99≤SLO则QPS全计入”替代。
- p50/p95/p99：按轮次报告请求延迟；有足够尾部样本再报p99.9。不平均分位数冒充合并分位数。
- BG：同一固定工作量完成时间/工作单元吞吐、CPU份额、runnable最长等待；压力生成器需要导出真实工作进度。
- fairness：每租户进度与slowdown。不同业务的原始QPS不可直接相加；吞吐几何均值需同口径归一化，并逐场景同时展示。
- overhead：Agent/执行服务各自CPU时间、RSS、BPF map内存、context switches/migrations、PMU采样成本；request成本与测量窗口严格对齐。
- reliability：scx退出/失速、错误率、丢失观测、策略发布/恢复时延、冲突与失败率。

内部初始门槛：quiet吞吐回归不超过5%；主noisy场景配对收益CI方向为正；BG进度比例和最长等待门槛在pilot后按业务预算预注册。不能把设计护栏当硬实时保证。如果尚未设定BG底线，不发布“公平优化”结论。

BG相对进度定义为同一block、同工作单位/CPU池/场景中优化臂BG工作率除以A0工作率，窗口与业务测量窗口相同；该比值仅用于离线评估。在线保护使用pilot冻结的绝对最小工作率（单位/秒）、观察窗口和最长runnable等待，不假设Agent能观察当前未运行fair的反事实。不同BG工作单位按租户分开检查，不能把不兼容计数相加。

## 6. 执行流程与无效规则

1. 先用3–5个pilot block查工具、缓存预热、client饱和、BG数据和方差；pilot不能混入正式表。
2. 冻结构建/配置/样本量/随机种子/无效标准/主指标。旗舰初值20 block、每臂预热10s、测量60s；相位实验使用更长连续时间线。
3. block内随机或平衡臂顺序，避免固定A→D与温度/缓存时间相关。写出真实顺序；切换后确认旧loader、BPF link、cgroup动作均已恢复。
4. 所有臂使用相同初始化：数据集、暖缓存策略、连接建立、干扰启动/停止；记录必要washout。
5. 每轮独立产生环境、策略、业务直方图、BG进度、stdout/stderr、exit status及哈希。
6. 轮次结束做所有权/残留检查。发布、清理失败即停止后续受污染轮次并记录。

基础设施无效示例：客户端未启动、被外部重启、监控文件损坏且指标不可恢复。调度器watchdog、策略导致超时/OOM、Agent崩溃是**系统失败结果**，不以INVALID从分母消失。保留失败率、请求损失和业务可用性；若无法给出定义良好的性能分数，单列失败并避免只比较幸存样本。

不得按QPS低/方差大删除样本，也不得“跑到20个成功轮”而隐藏重试。配对缺失时保留完整试验账本，按预注册规则分析并做敏感性报告。

## 7. 统计与解释

对每block、每主对照，吞吐增益 `g_i = 100*(T_i/A_i - 1)`；延迟使用 `100*(L_i/L_Ai - 1)`，**负值表示改善**。表头统一方向，不混用“改善百分比”和“延迟变化”。吞吐mean配对百分比与总体中位数比值分别标明。

主报告给配对block bootstrap 95% CI（固定种子、重采样次数），同时给配对log-ratio的敏感性分析、胜/负轮数与原始散点。连续时间线不得把每秒观测当独立样本；有自相关时按运行/阶段重采样。CI重叠不是差异检验；直接对D与C的配对差值构造CI。

主假设预先限为少数对照；大量探索/消融注明探索性并考虑多重比较。双峰基线先检查条件变化/steal/client/频率等替代解释；配对本身不能消除所有混杂。单机成功不代表所有硬件普适；能做时增加独立机器/未见负载验证。

相位实验报告累计goodput、SLO违约面积、切换次数、进入稳定状态时间和恢复时间。学习版使用训练/验证/测试分组，不把同一次运行相邻窗口同时用于训练和测试。

## 8. 故障验证

独立于正式性能运行，验证：kill Agent、停止心跳、kill执行服务、无效/越界策略、generation冲突、双实例、PID/cgroup重建、目标迁出、PMU拒绝、日志盘满、跨域第二步失败、恢复失败、外部改值、CPU热插拔。观察默认fair接管、目标存活和后台恢复。

心跳需要在CLASS和ADAPTIVE都失效安全；检查旧class、vtime、slice和排队任务，不能只看cfg.flags。退出loader/服务能否detach取决于link实际持有与pin；集成验收读取内核状态/调度计数，不仅检查进程退出。

## 9. 原始数据与交付格式

```text
evidence/runtime/<experiment-id>/
  manifest.json          # 源码/dirty差异/内核/对象/工具/配置哈希
  protocol.json          # 预注册目标/阈值/随机种子/轮数
  schedule.csv           # block与实际arm顺序
  runs/<block>/<arm>/    # 原始输出/直方图/BG/时间线/退出状态
  attempts.jsonl         # 包含失败与重试的完整账本
  per_run.csv            # 可由原始输出重新生成
  comparisons.csv       # 明确baseline/metric/单位/CI方法
  summary.md             # 包括负结果、限制、失败率
  SHA256SUMS
```

manifest包括tested_code_commit、dirty_diff_sha256（如有）、kernel source/config/BTF、loader/daemon/BPF对象、依赖锁、完整参数/环境变量白名单、启动与测量时间、CPU/角色预算。可复现意味着原始输出能重算表格、相同构建可重新跑，不要求不同机器逐字节得到相同QPS。

证据校验区分：完整性验证、来源验证、运行能力、性能结论。缺任一关键输入返回INCOMPLETE；历史/回放必须标记，不能作为实时实验PASS。
